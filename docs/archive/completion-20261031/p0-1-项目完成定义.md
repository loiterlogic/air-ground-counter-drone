## 为什么先做这件事

项目里"完成"有多个互不兼容的口径：迁移 workstream 口径（W6 出口）、研究口径（W7/W8 判定成立）、软著口径（平台可用）。三个口径各有一批脚本和证据，**没有任何一个能单独回答"项目做完了吗"**。

不定标准就直接开工，会出现典型的返工：地图做完了发现主场景跑不通、面板做完了发现没有可展示的终态、演示脚本写完了发现没人知道该看什么。

**这一步只产出一份书面标准，不写代码。**

### 1.2 口径澄清：主场景的目标轴是 `static`（不换场景）

本文件早期草案曾以"目标需运动，否则反无人机叙事不成立"为选场理由，与最终选定的 `s04`（`target_motion: static`）**不一致**。按用户裁定，场景不变，口径改为：

- **主场景承载的能力**：静态障碍环境下的"空地协同抵近 + 持续跟踪终态"闭环，以及端到端可复现的**工程闭环**（一条命令起、跑到终态、落盘、干净退出）。
- **主场景不承载**：机动目标跟踪。该能力由回归场景 `s02_linear_none_nominal_track`（匀速直线）与 `s03_maneuver_none_nominal_track`（机动）承载，二者同为 `TRACKING_SUCCESS`。
- **后果**：对外表述不得把主场景当作"机动目标反无人机"演示；讲机动性须另取 `s02`/`s03` 的 run 产物，并如实标注场景 ID。

### 1.3 有效启动命令

**环境前置（缺一项即启动失败或不可信）**：

```bash
source /opt/ros/jazzy/setup.bash
source install/setup.bash                       # 需已 colcon build（install/ 存在）
export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST  # 本机多进程验证口径
export GZ_SIM_SYSTEM_PLUGIN_PATH="$PWD/install/agc_sim/lib:${GZ_SIM_SYSTEM_PLUGIN_PATH}"
```

> `GZ_SIM_SYSTEM_PLUGIN_PATH` **必须导出**：[world_bringup.launch.py](../../../src/agc_sim/launch/world_bringup.launch.py) 以 `EnvironmentVariable('GZ_SIM_SYSTEM_PLUGIN_PATH')` **追加**该路径，变量不存在时 launch 直接抛 substitution 失败；[episode_runner.py](../../../scripts/episode_runner.py) 亦为此显式导出。`ROS_DOMAIN_ID` 保持默认（非 0 域会使 lifecycle 服务数据面不通）。

**GUI（C3 定性/关键场景口径）**：

```bash
ros2 launch agc_task w6.launch.py \
  backend:=full \
  scene:=s04_static_static_obs_track \
  seed:=0 \
  gz_args:="-r -v 3 /home/chen/AGC/install/agc_sim/share/agc_sim/worlds/agc_world.sdf"
```

**headless（对照 / 快速回归）** —— 与上文唯一差异是 `gz_args` 加 `-s`：

```bash
ros2 launch agc_task w6.launch.py \
  backend:=full \
  scene:=s04_static_static_obs_track \
  seed:=0 \
  gz_args:="-s -r -v 3 /home/chen/AGC/install/agc_sim/share/agc_sim/worlds/agc_world.sdf"
```

**world 参数规则（易错，必须按此写）**：

1. `gz_args` 里**必须**含一个 `basename` 恰为 `agc_world.sdf` 的 token。世界文件由 [world_bringup.launch.py](../../../src/agc_sim/launch/world_bringup.launch.py) 按 **basename 匹配替换**：`world_obstacles=static` 时替换为运行期生成的 `/tmp/agc_world_static_obstacles.sdf`（base world + 由几何真源注入的 `pole_*`）。
2. 若 token 的 basename 不匹配，launch 会把运行期世界**追加**到末尾；若完全不写 `gz_args`，默认值已含 `install/agc_sim/share/agc_sim/worlds/agc_world.sdf`，等价可用。
3. 因此"含明确 world 参数"指的是**上表的 install 路径**，不是占位符 `<world>`。

**一键入口**：`./run_demo.sh`（P1-2 交付后成为唯一对外命令，见 [P1-2](p1-2-一键演示入口.md#p1-2-goal)）。该脚本**当前不存在**（项目根无 `run_demo.sh`），在那之前上述 `ros2 launch` 即有效入口。

### 1.5 `start` 必须显式调用（不会自动开始）

`w6.launch.py` 及其 include **都不调用** `/agc/task/start`（launch 侧无该调用）。进程全部就绪后状态仍为 `IDLE`，必须外部触发：

```bash
ros2 service call /agc/task/start std_srvs/srv/Trigger '{}'
```

- 成功应答：`success: true`，`message` 以 `started: AIR_SEARCH` 开头（[task_manager.cpp](../../../src/agc_task/src/task_manager.cpp)）。
- 既有证据里 2 条 `IDLE` 终态的 s04 run（`20261016-s04...`、`20261018-s04...`）即"只起了栈、没调 start"的形态——`IDLE` **不是**场景失败，是未开始。
- 整链下 `start` 事务内部**还要等悬停**（`air_hover_timeout_s=45`，实测悬停发生在 start 后约 10–14 s），故该调用可能阻塞十余秒；超时回 `air_hover_timeout` 并落 `INFRA_FAILURE`。

### 1.6 期望终态与达标判据

| 项 | 判据 | 来源 |
|---|---|---|
| 状态 | `/agc/task/state.state_name == TRACKING_SUCCESS` | [AgcTaskState.msg](../../../src/agc_msgs/msg/AgcTaskState.msg) |
| 原因 | `reason_code == tracking_milestone` | [task_manager.cpp](../../../src/agc_task/src/task_manager.cpp) |
| 里程碑位 | `tracking_milestone_met == true` | 同上 |
| 抵近判据 | 车↔目标 2D 距离 `≤ d_track_m = 3.0 m`，且**连续** `t_dwell_s = 3.0 s`（仿真钟）成立 | `w6_base.yaml` → `task_manager`（两值均显式登记） |
| 逐拍合法性 | 每一拍都满足：目标新鲜（`target_max_age_s`，**0.5 s**）、`confidence_min`（**0.5**）、车地面 odom 未超龄（`car_odom_max_age_s = 1.0 s`，已登记）、`target_id` 未变；任一不满足即**清零重计** | `target_max_age_s` 与 `confidence_min` 是**节点代码默认值**（`w6_base.yaml` 的 `task_manager` 段未登记），车 odom 寿命门见 `w6_base.yaml`；C8 不降级为累计时长 |

**几何自洽性（可静态复核，解释"为什么这个场景能收敛"）**：任务目标固定为 `(4.0, 3.0)`（`goal_follow_target=false`），到目标初始位 `(6.5, 2.5)` 的平面距离为 `2.55 m < 3.0 m`；车出生位到目标为 `11.85 m`。故终态判据可表达为"`target_xy_distance_m` 由约 11.9 m 收敛到 **≤ 3.0 m** 并保持 3 s"。

### 1.7 运行时长口径（三套时钟，互不冒充）

| 口径 | 归属 | 字段 / 参数 | 主场景取值 | 含义 |
|---|---|---|---|---|
| **任务仿真预算** | `task_manager` | `t_max_s` | **120.0 仿真秒** | 超过即 `MISSION_FAILED`(`TIMEOUT`)；C4：**超时算失败** |
| 终态驻留时长 | `task_manager` | `t_dwell_s` | 3.0 仿真秒 | 连续满足才成功 |
| 启动等待 | launch | `own_px4_delay_s`/`intruder_px4_delay_s` + 就绪门 | **约 45–60 s 墙钟（待实测确认）** | PX4 错峰 25/35 s，再等空中 odom 新鲜与悬停 |
| 墙钟看门狗 | 演示脚本 / runner | `--duration` / `--timeout` | **待 P1-2 预登记** | 与上面两项不同源，不得互相替代 |
| 进程时长 | `run_logger` | `duration_s`（`duration_kind=process_wall_incl_warmup_shutdown`） | **待实测** | 含启动等待与关停，**不等于**任务时长 |

**可判定的上限口径**：单次主场景 run 的**任务**时长以 `t_max_s = 120` 仿真秒为硬上限；**墙钟**上限尚无实测依据，由 P1-2 在演示入口里预登记后回填。

> 既有 s04 成功 run 的 `duration_s` 为 **16.00–17.57 s**（进程墙钟，RTF 0.836–0.916），但那些全部是 `lightweight` 后端、无 PX4 启动等待，**不得**当作 `backend:=full` 的时长预算。

## 二、演示闭环（6 段）

**顺序纠正**：`metrics/summary.json` 由 `run_logger` 在**进程收到 SIGINT、`spin` 返回后**的 `finalize()` 写出（[run_logger.cpp](../../../src/agc_task/src/run_logger.cpp)）。因此"结果落盘"必然在"停止"**之后**，不是之前。早期草案把"⑤ 结果 → ⑥ 退出"写反，按下表为准。

| 段 | 内容 | 外部观察方式 | PASS | FAIL / 已知陷阱 |
|---|---|---|---|---|
| **① 启动** | 一条命令起世界 + 车 + 目标 + 桥 + 任务层（整链另含 2×PX4/Agent/空中链路），并显式 `start` | ①`ros2 topic hz /clock`；②`ros2 topic echo /agc/task/state --field state_name --once`；③`ros2 service call /agc/task/start std_srvs/srv/Trigger '{}'` | `/clock` 在推进，`/agc/task/state` 有消息，start 应答 `success: true` 且 `started: AIR_SEARCH` | **判为"启动失败"**：start 返回 `reset_failed` / `reset_indeterminate` / `air_hover_timeout`，或 launch 因缺 `GZ_SIM_SYSTEM_PLUGIN_PATH` / 工具链缺失而拒启动。**`ros2 launch` 的退出码只反映停止方式，与任务成败无关** |
| **② 搜索** | `AIR_SEARCH → TARGET_ACQUIRED`，无人机发现并持续提供目标 | `ros2 topic echo /agc/task/state --field state_name`（连续看跳变）；`--field target_obs_age_s`、`--field target_id` | 出现 `TARGET_ACQUIRED`（或已进入后续态），`target_id` 非空，`target_obs_age_s ≤ 0.5` | 长期停在 `AIR_SEARCH`：目标链路无数据（整链查 `/agc/targets` 与 `/agc/air/odom` 新鲜度）。注意 `AgcTaskState` **不含** `confidence` 字段，置信度不可从该话题观察 |
| **③ 跟踪** | `TARGET_ACQUIRED → GROUND_APPROACH`，车抵近 | 同上 `--field state_name`；`--field target_xy_distance_m` | 出现 `GROUND_APPROACH`，且 `target_xy_distance_m` 单调下降到 `≤ 3.0` | 停在 `TARGET_ACQUIRED`：唯一执行口无输出（`/agc/ground/cmd_vel` 无回环 → 命令链未活） |
| **④ 终态** | 到达 `TRACKING_SUCCESS` | `--field state_name` 与 `--field reason_code` | `state_name == TRACKING_SUCCESS` 且 `reason_code == tracking_milestone` | 落 `MISSION_FAILED`(`TIMEOUT`) = 任务失败（C4），照实计入；落 `INFRA_FAILURE` = 门禁失败，单列、不计入成功率 |
| **⑤ 停止与清理** | `Ctrl-C`（SIGINT）停止，进程组回收 | `ps -eo pid,cmd \| grep -E "[i]nstall/agc_\|[M]icroXRCEAgent\|[p]x4_sitl\|gz sim\|[p]arameter_bridge\|[s]tatic_transform_publisher"` | 输出为空；`Ctrl-C` 后无孤儿 | 只杀父 PID 会留 `gz sim`/`px4`/Agent/桥孤儿（污染下次 run 的 participant 创建）。**不得** `pkill -f`（会匹配到 shell 自身） |
| **⑥ 结果落盘** | `run_logger` 落 `metrics/summary.json`（在 ⑤ 之后） | `ls $RUN/metrics/summary.json` + 读 `terminal_state` / `shield_infeasible_rate` / `reset_failure_rate` | 文件存在，`run_id` 与本 run 一致，`terminal_state == TRACKING_SUCCESS`，两个 C9 字段为数值 | `run_id` 不匹配 = 读到了别的 run（`run_id` 唯一且目录独占创建，不存在覆盖）。缺任一 C9 字段 = C9 不满足 |

**三种"成功"不混淆（本文件的核心口径）**：

| 说法 | 含义 | 判据 |
|---|---|---|
| 命令启动成功 | launch 进程起来、话题/服务在 | ① 的 PASS 条件 |
| 任务成功 | 状态机到 `TRACKING_SUCCESS` | ④ 的 PASS 条件 |
| 清理成功 | 停止后无残留、产物已落盘 | ⑤ + ⑥ 的 PASS 条件 |

任一项单独成立都**不得**表述为"主场景跑通"；三者同时成立才算一次完整闭环。

## 五、"项目完成"的一句话定义

**项目"完成"= `s04_static_static_obs_track` 在 `backend:=full` 下，用一条对外命令（`./run_demo.sh`）就能从干净环境跑到 `TRACKING_SUCCESS`，过程中 6 段演示闭环全部可外部观察，停止后无残留且 `metrics/summary.json` 含 C9 两项指标；同一闭环在 GUI 与 headless 下同 seed 一致；这两张有用途的地图、陌生人可照 README 复现、静态/离线测试全绿、无硬约束违规——上述全部成立。**

拆分即[完成清单](#p0-1-checklist) D1–D10；未列入的（论文结论、实机、真实视觉、物理命中）按[已知缺口](#p0-1-gaps)如实标注，不计入"完成"。
