# 整链排障速查（`backend:=full`）

> 面向"跑一批实验"的**可执行检查单**。故障判据与根因细节见 ADR，本文只给**判别顺序与处置**。
> 相关决策：[ADR-0005](../adr/0005-px4-toolchain-and-link.md#top)（uXRCE 链路）、[ADR-0019](../adr/0019-lifecycle-and-startup-robustness.md#top)（姿态字段序）、[ADR-0027](../adr/0027-uxrce-startup-reproducibility.md#top)（残留孤儿 / 运行前清场 / infra 重试）、[ADR-0014](../adr/0014-task-fsm-and-scenario-transaction.md#top)（capture 终态语义）、[ADR-0028](../adr/0028-dds-discovery-range-and-transport.md#top)（DDS 发现范围按能力探测）。

## 0. 三条环境铁律

> **2026-11-04 修订（推翻旧铁律①）**：旧版要求"必须 `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST`"。
> 该规则**隐含一个从未写出的前提**：`lo` 带 `IFF_MULTICAST`。本机 WSL2 内核**不满足**该前提
> （`/sys/class/net/lo/flags == 0x9`，只有 `UP|LOOPBACK`），于是"铁律"在这台机器上**不可依赖**——
> 1:1 拓扑下**稳定零送达**（多进程拓扑偶尔能通，这正是它历史上"忽好忽坏"的来源）。
> **规则已改成"按能力探测"**，判据与实测矩阵见 [2d-2](#dds-transport)，
> 唯一决定点：`scripts/demo/dds_transport.py`（`run_demo.sh` / `episode_runner` / 测试共用）。

| 项 | 值 / 做法 | 原因 |
|---|---|---|
| `ROS_DOMAIN_ID` | **保持默认 0** | 自设非 0 域（实测 77/81）→ lifecycle **服务数据面不通**（`ChangeState` 一律超时），话题却正常 |
| `ROS_AUTOMATIC_DISCOVERY_RANGE` | **按 `lo` 能力探测，不写死**：`lo` 有 `IFF_MULTICAST` → `LOCALHOST` + 默认传输（原生 Linux 行为不变）；`lo` **无**组播 → `SUBNET` + `FASTDDS_BUILTIN_TRANSPORTS=SHM`（本机**唯一稳定**组合）。脚本自动完成，见 [2d-2](#dds-transport) | `lo` 无组播时 `LOCALHOST` **按拓扑不可靠**（1:1 稳定零送达，多进程偶通），`SUBNET`+UDP 则"配对成功但数据零送达"；只有 `SUBNET`+`SHM` 稳定。旧记录的"`SUBNET` 会间歇性全失效"是同一组播缺陷的另一面 |
| 清理进程 | **禁止** `pkill -f "<名字>"` | 模式会匹配到该 shell 自身命令行 → 自杀（Exit -1）。用 PID：`kill $PID`，或 `pgrep -f "xxx[y]"` |

**禁止写死 `LOCALHOST`**（[ADR-0028](../adr/0028-dds-discovery-range-and-transport.md#guard)）：
需要它的地方一律调 `dds_transport.apply()` / `env_for()`。全仓写死会被
`./run_demo.sh test` 的 `dds` 组直接判 FAIL——**这是机制拦截，不是劝告**。

**自查一条命令**（不需要跑任何 ROS 节点就能判）：

```bash
ip link show lo | grep -o MULTICAST || echo "lo 无 MULTICAST → 必须走 SUBNET+SHM，脚本已自动处理"
```

## 1. 启动前检查（每批必做，约 30 秒）

```bash
# ① 无本项目残留（含**桥节点与 tf**——它们不在 install/agc_* 下）
ps -eo pid,cmd | grep -E "[i]nstall/agc_|[M]icroXRCEAgent|[p]x4_sitl|gz sim|[p]arameter_bridge|[s]tatic_transform_publisher" | head

# ② 只读登记 DDS 共享内存数量；数量本身不能证明归属或故障原因
ls /dev/shm | grep -c fastrtps
# 禁止 glob 批量删除。没有本项目 ROS 进程，不代表所有段都归本任务。

# ③ 环境
echo $ROS_DOMAIN_ID                # 应为空或 0
export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST

# ④ 工具链二进制在位
ls -l toolchain/bin/MicroXRCEAgent toolchain/PX4-Autopilot/build/px4_sitl_default/bin/px4
```

> 共享内存清理不是默认预检或实验授权。只有明确授权、列出精确路径并证明归属与无活跃持有者后，才可处置对应残留；归属未知时停报，不批量删除（协作边界见 [ADR-0026](../adr/0026-leader-worker-collaboration-and-batch-authorization.md#top)）。
>
> ① 中的**桥 / tf 节点**是最易漏的一类：本体在 `/opt/ros/jazzy/lib/...`，命令行**不含** `install/agc_`。
> 正常路径下 runner 的进程组回收会收干净；只有**外部终止**（断网 / 宿主只杀 leader）才会逃逸为孤儿。
> `episode_runner` 已在每次 episode 前自动做同口径清场（[ADR-0027](../adr/0027-uxrce-startup-reproducibility.md#top)(g)），但**不**清 `/dev/shm`。
>
> **① 的判据要从"有没有进程"升级成"端口段有没有越界"**：`parameter_bridge` / `static_transform_publisher`
> 在上一轮被外部终止时会逃逸成孤儿，**每跑一次再叠一批**，最终把 Fast DDS 端口顶出正常段（约 7000–7300）。
> 那时新起的客户端会打印 `Failed init_port fastrtps_port70xx: open_and_lock_file failed`，
> 于是"话题存在但收不到数据"——看起来像 DDS / QoS 故障，其实是**自己造的环境污染**。
> 完整判据、清理步骤与纪律见 [孤儿进程假象](#orphan-dds)。

| `/clock` 不推进 / `clock_not_progressing` | 无 `ros_gz_bridge` → 无 `/clock`；`use_sim_time` 节点时间冻结为 0 | 查桥进程是否在跑；查 gz 是否启动成功 |

## 2b. uXRCE participant 创建长尾（ADR-0027）

> 判别：清场 / 清 shm 后仍反复出现 `create entities failed: participant: 255`，且 agent 日志 `create_client → establish_session` < 0.05 s、`establish_session → participant created` > 1 s。

| 项 | 当前默认 / 做法 | 说明 |
|---|---|---|
| 慢阶段 | agent 侧 **DDS participant 创建**（不是 XRCE 会话） | 失败整链 own 1.28–3.09 s；intruder 0.72–0.76 s |
| 触发条件 | 启动期 DDS 发现图繁忙 + 该 agent 的**首个** participant | 20 个 ROS 节点即可复现 4.86 s；CPU busy loop 只到 90 ms |
| 修复 | **own 25 s / intruder 35 s 错峰**（主修复）+ `backend=full` 的 `/agc/air/odom` 就绪门 | A4 no-warmup 5/5（own 694–704 ms）；warmup 可选、默认关闭 |
| 就绪门 | `episode_runner` 对 `backend=full` 等 `/agc/air/odom` 新鲜（1 s）后才 start | 否则 `air/reset_phase service unavailable` → IDLE |
| 验收 | `--infra-retries 0` 连续冷启动；own / intruder participant < 1 s、无 `create entities failed`、达任务终态 | 5 连 + 2 默认回归已通过（ADR-0027） |
| 回退开关 | `px4_warmup:=false`、`own_px4_delay_s:=…`、`intruder_px4_delay_s:=…` | 仅用于 A/B；默认不要改回 12/25 |

**不要**：用 runner 重试代替修复；改 PX4 1 s 预算 / pin；把 `FASTDDS_BUILTIN_TRANSPORTS=UDPv4` 当唯一修复（首跑仍失败）。

<a id="orphan-dds"></a>
## 2c. 孤儿进程会伪造"DDS 坏了"的假象（2026-11-03 实测，代价极高）

> **这一节是本项目排障里最容易骗过自己的坑**：症状看起来是 DDS / QoS / PX4 故障，实际是**自己上一轮留下的进程**。

**症状**（任一条即可疑）：

- `ros2 topic list` 里 `/px4_1/*` 只剩 1 个话题，但 agent 日志明明 `datawriter created` 成功；
- 同一话题 `ros2 topic hz` 有数据，而节点订阅收 0 条；
- 新起的 `ros2` 客户端打印
  `RTPS_TRANSPORT_SHM Error ... Failed init_port fastrtps_port70xx: open_and_lock_file failed`；
- 系统 load average 莫名 10–26，但同时看不到明显 CPU 大户。

**判据**：看 Fast DDS 端口号有没有**越过正常段**。正常约 `7000–7300`；实测被孤儿顶到 **8163** 之后，新进程再也加入不了 DDS。

**病因**：`static_transform_publisher` 与 `parameter_bridge` 从 `/opt/ros/jazzy/lib/...` 启动，命令行**不含** `install/agc_`，所以按 `install/agc_` 过滤的清理会**全部漏掉**。它们持续占用端口段，且每次重跑再叠加一批。

**处置**（按 PID，禁止 `pkill -f`）：

```bash
ps -eo pid,args | grep -E "[s]tatic_transform_publisher|[p]arameter_bridge|[M]icroXRCEAgent|[p]x4_sitl|gz sim" | head
# 逐个 kill PID，然后：
ps -eo pid,args | grep "ros2cli.daemon" | grep -v grep | awk '{print $1}' | while read p; do kill -9 "$p"; done
# 等 5–10 s 让持有者退出，再分两次清 shm（一次删不掉是正常的）
rm -f /dev/shm/fastrtps_* /dev/shm/sem.fastrtps*; sleep 5
rm -f /dev/shm/fastrtps_* /dev/shm/sem.fastrtps*; sleep 3
ls /dev/shm | grep -c fastrtps      # 必须为 0 才算干净
```

**纪律**：任何"这次好像 DDS 不通"的结论，**在 shm 计数归零、孤儿清零之前不得采信**。2026-11-03 的多轮自相矛盾结论，复盘后大半是这一条造成的。

<a id="type-mismatch"></a>
## 2d. 同话题两种消息类型 → 订阅端静默收 0 条

**症状**：话题在 `ros2 topic list` 里存在、`ros2 topic hz` 有数据，但某个节点回调**一次都不触发**（例如 `target_takeoff_guard` 恒报 `have_gt=0`）。

**判据**：

```bash
ros2 topic info /agc/gt/intruder_uav -v | head -3
# Type: ['geometry_msgs/msg/PoseStamped', 'nav_msgs/msg/Odometry']   ← 成了列表就是两种类型
```

DDS 按 **类型** 匹配。同一话题上一旦有两种类型，各自只会投递给自己的同类型订阅者；另一种**静默收不到**，不报错。

**实例**：`/agc/gt/<entity>` 由 `gt_bypass` 以 `geometry_msgs/PoseStamped` 发布（唯一来源）。若某节点按 `nav_msgs/Odometry` 订阅，就会永久收不到。

**纪律**：新增订阅 `/agc/gt/**` 的节点时，**先看发布端类型**（`src/agc_perception/src/gt_bypass.cpp`），不要凭"odom 更自然"去猜；`CMakeLists` 依赖随之改（`nav_msgs` → `geometry_msgs`）。

<a id="dds-transport"></a>
## 2d-2. `lo` 无组播 → 本机 DDS 只能走 `SUBNET`+`SHM`（2026-11-04 实测，机制已定论）

> **这一节推翻了旧的"必须 LOCALHOST"铁律**。旧规则"必须 `LOCALHOST`"隐含 `lo` 带 `IFF_MULTICAST`，
> 本机不满足，于是**照规则做反而全链零送达**。

### 事实（可复现，不依赖业务代码）

| 观测 | 命令 | 本机结果 |
|---|---|---|
| `lo` 标志位 | `/sys/class/net/lo/flags` → `0x9` | 只有 `UP\|LOOPBACK`，**无 `IFF_MULTICAST(0x1000)`** |
| 组播回环反射 | 见下方"逐层对照" | 部分组合静默丢弃 |
| 两最简 rclpy 节点对拍 | `pub.get_subscription_count()` / 订阅端计数 | 只有 `SUBNET`+`SHM` 能到 238/238 |

**逐层对照**（UDP 组播，同一台机；`join` = `IP_ADD_MEMBERSHIP` 的接口，`send` = `IP_MULTICAST_IF`）：

| join 成员资格 | 发送接口 | 结果 |
|---|---|---|
| `0.0.0.0`（任意接口 = Fast DDS 默认） | `lo`（`127.0.0.1`） | ❌ 丢弃 |
| `0.0.0.0` | `eth3`（`10.21.247.243`） | ✅ |
| `lo`（`127.0.0.1`） | `lo` | ✅ |
| `eth3` | `eth3` | ✅ |

**机制定论**：`0x9` 的 `lo` 不参与 `IN_DEV` 的组播成员资格计算，凭 `0.0.0.0` 加入的组套接字
**不会在 `lo` 上收到**任何人发的组播包；而 Fast DDS 对**内置发现**用 `0.0.0.0` 加入。
于是 `SUBNET` 下常见"发现能配对（`get_subscription_count()` 会到 1）但**用户数据零送达**"——
与本机历史记录里 `matched=1 / heard=0` 的形态一致。

**`LOCALHOST` 是"不可靠"而不是"必然全废"**（实测，别把结论说满）：它的失败**取决于拓扑并发度**，
因为多个 participant 并存时，被丢弃的组播通告可能由别的 participant 侧信道"补上"：

| 拓扑（同策略 `LOCALHOST`） | 实测 |
|---|---|
| 1 发布进程 ↔ 1 订阅进程 | **0/1 稳定失败**（3/3 次） |
| 1 订阅 ↔ 2 发布进程 | 2/2 通过 |
| 1 订阅 ↔ 6 发布进程 | 5–6/6（3 次：5、6、6） |

这就是它**历史上时好时坏**的来源：`test_run_logger_mission_fco` 恰好是 **1:1 拓扑**，
所以在本机稳定失败；而人多进程的临时探针偶尔能通过，容易误判成"环境没事"。

**实测矩阵**（同上，数字 = 订阅端收到条数）：

| 发现范围 | 传输 | 送达 |
|---|---|---|
| `SUBNET` | 默认（UDPv4+SHM） | **0**（发现配对成功，用户数据走 UDP 被丢；SHM 段 `port7000` 两侧都映射，但数量不走它） |
| `SUBNET` | 仅 `SHM` | **238 ✅** |
| `SUBNET` | 仅 `UDPv4` | 0 |
| `LOCALHOST` | `SHM` / `UDPv4` / 默认（1:1 拓扑） | **0 / 0 / 0** |

### 处置（已自动化，不必手工 export）

选择依据改为**能力探测**，唯一决定点 `scripts/demo/dds_transport.py`：

```bash
# 看一下它选了什么（run_demo.sh 启动时也会打印同一行）
python3 -c "import sys; sys.path.insert(0,'scripts/demo'); import dds_transport as d; print(d.describe())"
# -> dds policy=subnet-shm (lo multicast=no, flags=0x9) -> ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET FASTDDS_BUILTIN_TRANSPORTS=SHM
```

已接入：`run_demo.sh`、`scripts/demo/start.py`、`scripts/demo/doctor.py`、
`scripts/episode_runner.py`、`src/agc_task/test/test_run_logger_mission_fco.py`。
需要钉死时用 `AGC_DDS_TRANSPORT_POLICY=auto|localhost-udp|subnet-shm|subnet-udp`。

**边界与例外**：

- `SHM` 只在**同主机**多进程间有效；跨机器仍须 UDP + 能用的组播网卡（本机 `eth3` 组播正常）。
- **多 worker 例外**：ADR-0024 要求**禁 SHM**（`/dev/shm` 不随 netns 隔离）。该场景由
  `episode_runner` 在探测结果**之后**显式覆盖为 `UDPv4`+`LOCALHOST`——"隔离优先于连通性"，
  是刻意的显式取舍，不是漏改。
- `ip link set lo multicast on` 本内核回报 `Operation not permitted`，**不是**可用修法。

被误读为"记录器逻辑错"）。修好后：该测试**无需任何手工 export**，连跑 8/8 通过；
`agc_task` ctest 6/6、全量 pytest 413 passed。

> **不要**把它 `skip` 掉：它的断言本身是对的，之前的失败**全部**来自本节环境缺陷。
>
> **纪律**：判定"DDS 到底通不通"时，**必须用与本测试同构的 1:1 拓扑**去探。用六个进程的
> 临时脚本探活会得到"能通"的错误结论（本页作者 2026-11-04 就踩了这一脚）。

<a id="no-magsim"></a>
## 2e. 无磁力计 → EKF 锁不住航向 → 目标机永不起飞

**症状链**：`Preflight Fail: Compass Sensor 0 missing` / `No valid data from Compass 0` → `Preflight Fail: Yaw estimate error` → EKF 不发布 `vehicle_odometry` → `intruder_driver` 收不到 odom → 不 ARM → 目标机停地面 → 全程 `AIR_SEARCH`。

> ⚠ **2026-11-03 更正：旧版末段「3D 距离 ≥ 量程 12 m → 感知恒盲」已失效。**
> 量程改为 **30.0** 后，目标停地面时 `√(26.17² + 14²) = 29.68 m` **仍在量程内**（余量仅 0.32 m），
> 感知照样有航迹（只是钉在地面某点不动）。⇒ 「目标没起飞」**只能**靠 `intruder_driver` 自身的
> `have_odom=False` 错误日志、或 `target_takeoff_guard` 的启动期守卫判定；
> **不得**再指望「感知致盲」间接暴露。

**根因**：PX4 官方 gz 机型 `x500`（→ `x500_base`）**没有 magnetometer 传感器**（只有 `air_pressure` / `imu` / `navsat`）。PX4 的 `sensor_mag_sim` 模块用 GPS 位置 + 世界磁场模型**合成**磁力计，但只在 `SENS_EN_MAGSIM=1` 时启动，而该参数**定义默认值就是 0**。

**修复**：`src/agc_task/config/px4_failsafe_lock.yaml` 的 `sensor_en_magsim: 1`（经 `lock_px4_failsafe_params.sh` 写入 `px4-rc.params`；该文件在 rcS 中先于 `px4-rc.simulator` 被 source，时机正确）。

**不要**用 `SYS_HAS_MAG=0` / `EKF2_MAG_TYPE=5` 绕过——实测那两条会让 `Ready for takeoff` 从 2 次降到 **0** 次（EKF 失去全部航向约束，连初始化都过不去）。

<a id="invalid-setpoints"></a>
## 2f. `invalid setpoints` → PX4 failsafe 盲降 → 己方爬不到起飞高度

**症状**（实测 3 次里 2 次）：

```
[mc_pos_control] invalid setpoints
[mc_pos_control] Failsafe: blind land
[failsafe] Failsafe activated
[health_and_arming_checks] Preflight Fail: No valid data from Compass 0
[health_and_arming_checks] Preflight Fail: Battery unhealthy
```

随后 `task_manager` 报 `等待起飞完成超时（45.0s 内未见爬升达 13.80 m：air_odom=1 z=3.39 base=-0.35）`——己方**已经在爬**（`Armed` + `Takeoff detected`），爬到 3–5 m 就被判 setpoint 无效、触发盲降掉回来。

**判别（关键）**：`invalid setpoints` 与 `Compass` / `Battery unhealthy` **同现**，且次数固定（实测各 17 / 3 条）。这三者是**同一个上游原因的三个下游症状**，不是三个独立故障：

- 根因是 **uXRCE DDS 拥塞**：己方 `takeoff_controller` 已在发 setpoint 时，**第二个 PX4 实例启动**（默认 +35 s）造成的 DDS 发现风暴冲掉 setpoint 流 → PX4 收到无效/断帧 setpoint → 自保盲降；
- 同一拥塞也让 `sensor_mag_sim` 的 mag 样本断流 → `No valid data from Compass 0`；
- 电池读数同理。

**实测相关性（3/3 一致）**：`invalid setpoints=0` 的那次是**唯一**跑到任务终态的一次；另两次都是 17 条、都在爬升被判死。

**处置顺序**（不要先改飞行高度 / 不要先怀疑磁力计配置）：

1. 按[「启动前检查」](#preflight) 清孤儿 + 确认 `fastrtps` 段归零（**这是第一位的**，实测本机绝大部分"间歇"都来自这里）；
2. 加大own / intruder 错峰（`own_px4_delay_s` / `intruder_px4_delay_s`），让第二个 DDS 参与者创建**避开**己方爬升窗口；
3. 确认 `SENS_EN_MAGSIM=1` 已生效（见 [2e](#no-magsim)）；
4. 仍复现再查 [participant 创建长尾](#uxrce-participant-long-tail)。

**不要**把 `t_max_s` 或墙钟预算当解药：实测把 `--timeout` 从 150 提到 300 只把 `wall_watchdog_timeout` 变成了**更诚实的** `air_hover_timeout` / `TIMEOUT`，失败数没变（0/3 → 0/3）。**预算只改变失败的报法，不改变失败。**

> **2026-11-04 补充：`air_hover_timeout` 是偶发的启动竞态，不是能力缺陷。**
> 同一条 `full` 整链回归（3 场景）首轮 2/3、其中 `s10` 报 `air_hover_timeout`
> （`ready=true`、`started=false`、`participant created` 已成功）；**单独重跑同一场景即通过**，
> 第二轮整链 **3/3 全绿**。所以：
> * 见到 `air_hover_timeout` **先重跑一次**再判定，别急着改起飞时序或预算；
> * 它属 **infra** 类（`outcome_class=infra_failure`），与"任务没打成"必须分开统计——
>   `tests/run_full_regression.py` 已把它们分成 `INFRA` / `FAIL` 两种标记。
> * 尚未定位到根因（可能是双 PX4 参与者与己方爬升窗口的竞态，见本节第 2 条）。**如实留作已知项。**

## 4. 一批跑完后的收尾

1. 核对 `metrics/arms.json` 的 `infra_retry_protocol`（`retried_runs` / `max_retries_used`）—— **infra 率必须随报告报出**，不得读作臂效应。
2. 核对 `metrics/perception_health.json`（`no_pose/rmax/fov` 占比）——`no_pose` 偏高说明空中位姿断供，按上文排查；`fov_*` 偏高查指向 / 姿态。
   **`rmax` 在 2026-11-03 之后不再是环境边界**：量程已由 12.0 改为 **30.0**（原推导见
   已退役的 `perception_sensors.yaml` 文件头，现登记处 = `air.yaml` standoff_follower 注释 +
   飞行高度规范 K1），站距带上沿 11.2 m 远小于量程上界
   `√(30²−dz²) ≈ 29.93 m`。若仍见 `rmax` 占比偏高，**说明是真问题**（目标被推到 30 m 外，
   例如布局变更未同步、或 `spawn_layout` 与场景覆盖冲突），**不再**可当作"已知边界"忽略。
3. 确认 `ps` 无残留（同[「启动前检查」](#preflight) ①）；若有，说明该批次有被外部终止的 run，需登记。
4. 作废批次**必须在产物内显式标注**（`arms.md` 顶部 / `INCOMPLETE.md`），禁止让后来人误读。

## 5. 多 worker 前的前置条件

当前 `sweep_stale_processes` **不区分 worker 归属**（按项目特征 SIGKILL）→ 同机并行时后启动者会杀掉先启动者的进程。
**在隔离手段落地前只允许单 worker 串行**（风险登记见 [ADR-0027](../adr/0027-uxrce-startup-reproducibility.md#top)(i)）。
