# 测试分层与可测性

> **本文件回答一个问题：一个判据该写在哪一层？** 写错层的代价不是"多跑几秒"，
> 而是**判据看起来存在、实际跑不动**。
>
> 约束类信息（硬约束 / 终态语义 / 接口语义）**只引用** [契约真源](../adr/0020-package-boundaries-and-runtime-topology.md#hard-constraints)，本文件不复述。

<a id="layers"></a>
## 1. 四层，按**运行前提**分（不是按重要性）

| 层 | 位置 | 运行前提 | 数量 | 何时跑 |
|---|---|---|---|---|
| **L1 离线冒烟** | `tests/run_smoke.py` 的 `GROUPS` | 什么都不用准备 | 9 组 | **每次提交** |
| **L2 单元测试** | `src/*/test/`（gtest）+ `scripts/tests/`（pytest） | 构建产物 + Python 环境 | 112 + 383 | **每次提交**（`colcon test` / `pytest`） |
| **L3 证据核查** | `tests/check_*.py` 的 `evidence` 类 | **需要 `experiments/` 历史证据** | 22 | 按需（复核历史结论） |
| **L4 整链验收** | `tests/check_*.py` 的 `needs_sim` 类 | **需要活着的仿真 / SITL** | 33 | 按需（里程碑） |

分类口径的**唯一实现**是 [`tests/checklib.py`](../../tests/checklib.py) 的 `check_categories()`；
`tests/check_doc_counts.py` 的判据 e / f 拿它跟文档对账，所以"文档写 22、实际 21"会让冒烟变红。

<a id="ratio"></a>
## 2. 必须说清的事实：**新 clone 只能跑 9.5%**

| 前提 | 数量 | 占比 |
|---|---|---|
| 什么都不用准备 | **6** | **9.5%** |
| 需 `experiments/` 历史证据 | 22 | 34.9% |
| 需活着的仿真 | 33 | 52.4% |

**这不是缺陷清单，是分层语义**。L3 / L4 是**一次性取证档案**：针对某个已结档的能力项
断言一次，价值是"历史可复核"，不是"每次提交都跑"。把它们当测试套件会得出
"新 clone 跑不动测试 ⇒ 代码坏了"的错误结论。

实测依据（2026-11-07）：用空证据根跑那 22 个 L3 核查，**21 个如实 FAIL**
（唯一 PASS 的是 obs 版本化，它自带样本）。

**真正的回归防线 = L1 + L2**。新 clone 上它们必须全绿；跑不绿就是真问题。

<a id="testable"></a>
## 3. 可测性：判定逻辑必须能脱离 ROS 单测

**反面教材**（2026-11-07 之前）：18 个节点类全部定义在 `.cpp` 里，没有 header。
后果是 gtest 只能覆盖 12 个小叶子库，而**任务 FSM、dwell 判据、捕获结算**这些
真有逻辑、最容易被顺手改坏的地方**零单元测试**——只能靠 L4 捞，而 L4 要活仿真。

**规则**：

1. **纯判定抽成 header 里的类**，不 include ROS 消息包，输入输出都是普通 struct。
   例：[`task_fsm.hpp`](../../src/agc_task/include/agc_task/task_fsm.hpp) ——
   一拍观测 → 一个 `TaskFsmDecision`；发话题 / 锁存 / 打日志仍归节点。
2. **判定与副作用分离**：节点只做 `buildInputs()` → `step()` → `applyDecision()`。
   副作用（发消息、置状态）不进判定，否则测试要起 ROS。
3. **不 include 消息包**：常量用本地 `namespace`，值一致性由一条读 `.msg` 原文的
   gtest 断言守护（见 `StateConstantsMatchMsgDefinition`）——比"两边各写一份、靠人同步"可靠。

**判据**：一个判定类若必须起 ROS 才能测，说明它没抽干净。

<a id="writing"></a>
## 4. 写一条判据前先问三件事

1. **它能在哪个层跑？** 跑不动的层等于没写（见 [2](#ratio)）。
2. **它是断言行为，还是断言源码文本？** 后者在重构时会误报——
   若必须断言源码形态，指向**实现所在**文件，并在注释里写明"函数搬了家要同步"。
   （例：`test_branch_ledger.py` 的 `apply_target_motion_override` 断言，
   `composition.py` 拆成门面后改指 `scene_loader.py`。）
3. **它能不能红？** 新加闸门必须实测注入一个违规、确认它报错，再移除。
   没验证过"能红"的闸门，与没有闸门等价——本仓有过多起"看着有保护、实际零覆盖"。

## 5. 现有闸门清单

| 闸门 | 断言什么 | 层 |
|---|---|---|
| [`check_doc_counts.py`](../../tests/check_doc_counts.py) | 文档里的 7 类计数（核查数 / 组数 / ADR 上限 / 三分类 / 可跑比例）与实况一致 | L1 |
| [`docs_link_check.py`](../../tests/docs_link_check.py) | 文档链接与锚点；**代码注释里的 ADR 引用**（禁裸路径 / 可解析 / 锚点存在 / 编号有篇目） | L1 |
| [`check_config_orphans.py`](../../tests/check_config_orphans.py) | `src/*/config` 下每个 YAML 都被引用（或登记为例外） | L1 |
| [`test_retirement_ledger.py`](../../scripts/tests/test_retirement_ledger.py) | 退役物不复活（文件 / 节点 / 配置 / 分支 / 参数） | L2 |
