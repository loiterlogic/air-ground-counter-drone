# 飞行高度分层与「按地图定高」规范

> 本文件是**工程规范**：规定 AGC 里"高度"一词的语义分层、反无人机场景的轨迹来源约束，
> 以及**一张新地图落地时如何推导它的固定飞行高度**。
> **不复述**契约：坐标系、参数入口、硬约束 C1/C2/C10 一律以
> [契约真源](../ROS2迁移交接文档.md#hard-constraints) 为准，本文件只**引用**。
> 依据 [ADR-0008](../adr/0008-air-trajectory-and-tracking-calibration.md#top)（C1 参数与契约真源变更）、
> [ADR-0008](../adr/0008-air-trajectory-and-tracking-calibration.md#top)（世界 ENU 高度唯一语义）、
> [ADR-0010](../adr/0010-safety-thresholds-and-failsafe.md#top) / [ADR-0009](../adr/0009-perception-truth-derived-and-vision-path.md#top)
> （空中安全层为**二维静态圆盘 + 垂直门控**，见 [§3.5](#perception)）、[ADR-0007](../adr/0007-scene-geometry-single-source-and-layout.md#top)（几何按地图单一真源）。

<a id="why"></a>
## 0. 这份规范要解决什么

历史上"高度"在同一个仓库里同时指过五件不同的事，而其中三件的数值**恰好都是 `2.5`**——
数字相同掩盖了语义不同，导致：改"跟踪高度"时以为改了"八字高度"、飞越障碍时以为抬高就能过去、
用固定巡航高度当视觉测距平面。本规范做两件事：

1. **把"高度"拆成互不冒充的层**，每层指定唯一真源（[§1](#layers)）；
2. **给出一条可复用的推导规则**：给定一张地图的几何，算出该地图的固定飞行高度（[§3](#rule)）。

并明确一条**反无人机场景的硬规则**（[§2](#no-fixed-trajectory)）。

<a id="layers"></a>
## 1. 高度的语义分层（每层一个真源，禁止互相冒充）

| 层 | 名称 | 真源（唯一） | 单位/基准 | 谁写 | 谁读 |
|---|---|---|---|---|---|
| **L0** | 世界 ENU z | Gazebo world `agc_world`（+z 向上） | m，绝对 | 物理引擎 / 场景复位 | 位姿、TF、`/agc/gt/*`、安全层、日志 |
| **L1** | 局部 NED | PX4 EKF2 local origin（**= episode 原点**，epoch 后首帧 odom） | m，**向下为正** | PX4 | `px4_adapter`（转 ENU）、`intruder_driver`（发 setpoint） |
| **L2a** | 目标机巡航高度 | `intruder_driver.cruise_alt_m`（场景**必须**显式声明） | m，**相对 L1 原点的上升量** | `scenarios.yaml`（场景） | `intruder_driver`（视觉路径已退役，原 `vision_target` 高度平面消费者不存在） |
| **L2b** | 己方机跟踪高度 | `standoff_follower.height` | m，**世界 ENU z（绝对）** | `air.yaml`（→ 本规范建议改为按地图派生，[§4](#where)） | `standoff_follower` → `/agc/air/tracking_ref` |
| **L2c** | 己方机起飞高度 | `takeoff_controller.takeoff_altitude_m` | m，**相对起飞时刻机体高度**（`launch_point_.z + 本值`） | `air.yaml`（同上） | `takeoff_controller` |
| **L2d** | 预设轨迹几何高度 | `trajectory_tracker.traj.height`（= 契约 C1 的 `h`） | m，**层高基准**：接管时刻 `z_offset_ = 机体 z − traj.sample(0).z`，`traj.height` 只决定**相对形状** | `air.yaml`（契约 C1，见 [ADR-0008](../adr/0008-air-trajectory-and-tracking-calibration.md#top)） | `trajectory_tracker` 的**兜底**参考 |
| **L3** | AGL / 真高 | **本项目不具备** | — | 无 | 无 |

### 1.1 三条必须记住的语义事实

- **L3（AGL）没有真源**。PX4 的 `VehicleLocalPosition.dist_bottom` 需要下视测距传感器
  （本项目无），地形跟随需要 SRTM 地形库且精度约 10 m 量级——**在本项目 3–10 m 的尺度上不可用**。
  ⇒ 任何"高度"在本仓都**不是**真高；写文档/写结论时不得称 AGL。
  外部依据与边界见 [round-7 外部参考](../../.coordination/task/20261102-002-n1-vision-minimal-loop/round-7/evidence/external-references.md#external-references)（E9 / E11）。
- **L2a 不是世界高度**。`cruise_alt_m` 是"相对 episode 原点的上升量"；世界绝对高度 = 原点世界高度 + 本值，
  而原点高度由 EKF 初始化决定、**跨 run 不可复现**（实测漂移 −0.50…+0.44 m）。
  世界放置值另有其家（`spawn_layout.yaml` 的 `target.z`，PX4 attach 前的瞬态，**不叠加**）。
  该裁定见 [ADR-0014](../adr/0014-task-fsm-and-scenario-transaction.md#top) 与 H0 任务记录。
- **L2a 的唯一权威输入与别名规则**（H0 标定结论，2026-11-02）：
  **唯一权威输入** = `cruise_alt_m`。`alt_m` 降为**弃用别名**：仅在 `cruise_alt_m` 未显式给出时生效；
  两者同时显式且不相等 → `intruder_driver` **拒绝启动**；两者都缺 → 同样拒绝（不静默取缺省）。
  每个 run 的 `scene_manifest.json` 须记 `effective_params.cruise_altitude` 四项：
  生效值 `effective_m` / 来源 `source`（`base`|`scene`）/ 基准 `datum=episode_origin_ned` /
  别名冲突 `alias_conflicts`，并显式登记 `world_enu_absolute: false` 与 `stacks_on_spawn_z: false`。
  `assertions()` 的 `cruise_altitude_single_valid_source` **启动前**拒绝歧义配置。
- **L2d 只有"兜底"意义**。`trajectory_tracker` 的参考来源优先级是
  `tracking`（感知驱动，来自 `/agc/air/tracking_ref`）> `hold`（已获目标后失效）> `base`（预设轨迹兜底）。
  反无人机场景禁用固定轨迹后（[§2](#no-fixed-trajectory)），**L2d 不再是决定飞行高度的量**。
- **`acquired_` 判据 = 连续新鲜，不是一帧**（2026-11-03 修正）。
  `trajectory_tracker` 的"已获目标"状态须在**连续 `latch_hold_s`（默认 3.0 s）**满足新鲜度后才置位；
  任一拍失新鲜即清零（**不累计断续**）。旧判据"收到一帧新鲜航迹即置位"会把**偶然看见**当成**已捕获**，
  实测后果是八字偶然扫进量程看见 1 帧后立刻失新鲜 → 永久 `hold` → 全程无目标 → `TIMEOUT`。
  契约 C10 的"过期即冻结"针对**已捕获目标后**失联；"一帧看见"**不等于**"已捕获"。
  本判据放宽的是**捕获的定义**，**不是冻结的语义**——冻结仍在过期后立即生效。

## 2. 反无人机场景禁用固定轨迹（**硬规则**）

> **用户 2026-11-02 17:12 原话**：「各种无人机固定轨迹是用来确定之前流程的，反无人机场景直接禁止使用，
> 目前用不上了。」

### 2.1 规则

1. **反无人机（counter-UAV）场景不得选择任何"预设固定轨迹"作为己方机参考来源**。
   当前实现载体是 `air.yaml` 的 `trajectory_tracker.trajectory_plugin`，可选值见
   [`src/agc_control/plugins.xml`](../../src/agc_control/plugins.xml)：
   `LinearTrajectory` / `CircularTrajectory` / `HelicalTrajectory` / **`Figure8Trajectory`** /
   `HoverTrajectory` / `StepTrajectory`。
2. **不是删插件**：插件全部保留——它们是**流程验证 / 回归基线**用的。禁止的是**在反无人机场景里选它们**。
3. 反无人机场景的己方机参考**必须由任务/感知驱动**，即下面这条已有通路：

```
/agc/targets ──> standoff_follower ──/agc/air/tracking_ref──> trajectory_tracker ──> LQR ──> PX4
                    (height = L2b)                              (插件仅兜底)
```

   代码锚点：`standoff_follower.cpp`（订阅 `/agc/targets`、发布 `/agc/air/tracking_ref`，
   `ref.pos.z() = height_m_`）；`trajectory_tracker.cpp`（订阅 `/agc/air/tracking_ref`，
   `tracking_ref_timeout_s=0.5`；参考来源裁定 `tracking / hold / base`）。
4. **兜底插件必须换成不产生运动的实现**：反无人机场景应选 **`HoverTrajectory`**
   （保持接管位置、无速度前馈），**不得**让 `Figure8Trajectory` 留在兜底位上——
   否则一旦 `tracking_ref` 超时 0.5 s，飞机会开始按八字飞走。
   选 `HoverTrajectory` 后 `traj.*` 段（`height` / `rx` / `ry` / `speed` / `center_*`）**全部失效**
   （该插件不读 `ParametricTrajectory` 的参数；它只读 `use_hold_z` / `hold_z`）。

### 2.2 「禁用后己方机高度由谁决定」——明确回答

| 问题 | 答案 |
|---|---|
| 反无人机场景禁用固定轨迹后，己方机参考轨迹由谁生成？ | **`standoff_follower`**（消费 `/agc/targets`，输出 `/agc/air/tracking_ref`）→ `trajectory_tracker` 直采为 `effective` 参考 |
| `traj.height` 是否还影响该场景？ | **不影响飞行高度**。它只在 `base`（兜底）模式下被采样；禁用 Figure8 并改 `HoverTrajectory` 后，`traj.*` 整段不被任何插件读取 |
| 那么己方机实际飞行高度是哪个参数？ | **`standoff_follower.height`（L2b）**；`takeoff_altitude_m`（L2c）决定"进跟踪前的悬停/接管高度"，两者应一致或按 [§3](#rule) 有序抬升 |
| 是否需要改契约 C1？ | **不需要**——改 L2a / L2b / L2c 都不触碰 C1。**只有**改 `traj.height` 才需要改 C1 + [ADR-0008](../adr/0008-air-trajectory-and-tracking-calibration.md#top)，那超出 Worker 权限 |

<a id="rule"></a>
## 3. 按地图定高的推导规则

### 3.1 先算对"该算的 H_max"：**作业包络内的最高障碍**

全图最高障碍 `H_max_map` **不是**定高的依据——它可能离作业区几十米，抬高去"越过"它既无必要也做不到。
定高依据是**己方机在水平方向可能到达的区域**里的最高障碍顶 `H_max_env`：

```
H_max_env(map, scene) = max{ z_top(o) : o ∈ obstacles(map),
                             dist(o, Envelope(own)) = 0 }
Envelope(own) = 目标位置/路径 ⊕ safe_max  行 ∪  fig8 足迹（仅流程验证场景）
```

- `dist(·)` 用**水平**矩形距离（障碍按 part 的水平 AABB，与 `world_map.obstacle_safety_radius` 同源）；
- `⊕ safe_max` = 以目标当前/规划路径为中心、半径 `standoff_follower.safe_max` 的邻域；
- **流程验证场景**另加 `fig8` 足迹（`x ∈ ±rx`、`y ∈ ±ry/2`）。

> 例：`yard` 的 `H_max_map = 10.55 m`（`admin_block`），但它距目标 32.29 m、远在包络之外；
> `s04`（静止目标）的 `H_max_env` 只有 **2.10 m**（`pipe_rack_e`，距目标 10.34 m）。用 `10.55` 定高会把两机抬到没必要的高度，
> 反而恶化感知几何（[§3.3](#perception)）。量化见
> [`height-survey.json`](../../.coordination/task/20261102-002-n1-vision-minimal-loop/round-7/evidence/height-survey.json)。

### 3.2 三个约束、两条不等式

记 `h_t` = 目标机高度（L2a 的**绝对**世界值 = 原点高度 + `cruise_alt_m`），
`h_o` = 己方机跟踪高度（L2b），`dz = h_o − h_t`，`S = safe_max − hysteresis`（当前 `11.2 − 1.0 = 10.2 m`，停止趋近点）。

| 编号 | 约束 | 来源 | 不等式 |
|---|---|---|---|
| **K1** | 感知量程（**三维球**） | 历史登记处为 `perception_sensors.yaml` 的 `range_max_m = 30.0`（已随 `perception` 轴于 2026-11-06 退役）；现登记处为 `air.yaml` 的 `standoff_follower` 注释与本规范本节 | `√(R² − dz²) ≥ S` ⇔ `|dz| ≤ √(R² − S²)` = **28.21 m**（R=30.0，S=10.2）。⚠ **不生效**：`/agc/targets` 的发布者 `gt_adapter` 不做几何门控，`air_perception` 已删除——K1 仅作**配置自洽性**验算，不是运行期限制 |
| **K2** | 相机垂直视场 | 历史同为 `perception_sensors.yaml` 的 `vfov_deg = 70`（±35°），`boresight_body = [1,0,0]`（前视）；随 K1 同一文件退役 | `|dz| ≤ S·tan(vfov/2)` = **7.14 m**（当前比 K1 松，K1 先绑定） |
| **K3** | 垂直净空 | 空中安全层**垂直门控**（[ADR-0010 (j)](../adr/0010-safety-thresholds-and-failsafe.md#vertical-gate)，2026-11-04） | `h_o ≥ H_max_env + c_clear`（**`c_clear` 按地图取值，见 [按地图定高](#ruling-20261102) U1**；门控后降为**推荐高度**——低于顶面时圆盘仍生效，见 [§3.5](#perception)） |

另有**目标侧**的硬上界（[§3.4](#capture)）：

| **K4** | 捕获/干扰包络 | `w6_base.yaml` 的 `applicable_max_alt_m = 2.009`、`jam_envelope_max_alt_m = 2.0` | `h_t − car.z − launcher_height_m ≤ 2.009` |

> **两机同步抬升是"免费"的**：K1/K2 只约束 `dz`，不约束绝对高度。
> 只要 `dz` 不变，感知几何**逐值不变**（水平预算仍 `√(R² − dz²)`，视线俯仰角不变）。
> 变化的只有：① 相对 `H_max_env` 的净空（K3）；② 目标机是否还在捕获包络内（K4）。
> 这是本轮最重要的结构性结论——它意味着"抬高"必须**同时**问"抬谁的、抬多少、捕获还成不成立"。

<a id="perception"></a>
### 3.3 抬己方机 ≠ 提高可见性（反直觉但必须写明）

目标通常**低于**己方机（`h_t ≈ 0.9–1.9 m`，`h_o = 2.5 m` ⇒ `dz ≈ +0.6…+1.6 m`）。
己方机越高、`dz` 越大 ⇒ 视线越"低头"⇒ 越靠近 `vfov` 下沿、三维斜距越大、水平预算越小：

| `dz` | 水平预算 `√(900−dz²)`（R=30 m） | 停止点 10.2 m 是否在球内 | 视线俯仰角 @10.2 m | `vfov ±35°` |
|---|---|---|---|---|
| +0.5 m | 29.996 | ✓ | +2.8° | ✓ |
| +2.5 m | 29.90 | ✓ | +13.8° | ✓ |
| +10.0 m（只抬己方机到 12 m） | 28.28 | ✓ | +44.4° | **✗** |
| +28.2 m | 10.20 | 临界 | +70.1° | ✗ |

⇒ **只抬己方机、不抬目标机，是错误方向**——但**真正的绑定约束已从 K1 换成 K2**（相机垂直视场）：
`dz > 7.14 m` 时目标出垂直视场（`+44.4° > 35°`），而不是被量程拒绝。
量程放宽到 30 m 后，K1 的 `|dz|` 上限是 **28.21 m**，K2 的 **7.14 m** 先绑定。
⚠ 同前：在 `gt_adapter` 单源下这些门控**都不在运行期生效**，本表用于回答「若恢复通道链路，约束会从哪来」。

<a id="capture"></a>
### 3.4 抬目标机撞上捕获/干扰包络（K4）

`capture_adjudicator` 的网弹道包络上界是**由物理参数解出来的**：
`(v0·sinθ)²/(2g) = (6.5·sin75°)²/(2·9.81) ≈ 2.009 m`（`w6_base.yaml` 注释原文）。
`jam_envelope_max_alt_m = 2.0` 同理。⇒ **目标机抬到 ~2 m 以上，`CAPTURE_NET` 与 `JAM_*` 立即不可达**
（`gateStatus` → `kOutOfApplicableRange`），capture/jam 场景会全部退化为 `TIMEOUT`。

要把目标机抬到任意高度，必须**重标定网发射物理**（`net_v0_mps` / `net_angle_deg` / `net_g`）
并重算包络——那是 [ADR-0011](../adr/0011-interception-and-fire-control.md#top) 的口径问题，**不是配置微调**。

### 3.5 高度如何进入避障：**垂直门控**（2026-11-04 已落地）

空中安全层是**二维静态圆盘**（[ADR-0010](../adr/0010-safety-thresholds-and-failsafe.md#top) / [ADR-0009](../adr/0009-perception-truth-derived-and-vision-path.md#top)）：
`SafetyShield::apply` 把障碍当作 XY 平面上半径 `safety_radius + obstacle_margin(2.5) + dynamicMargin(0.7)` 的圆盘。
历史上圆盘**不含 z**（每个障碍 = 无限高圆柱）；[ADR-0010 (j)](../adr/0010-safety-thresholds-and-failsafe.md#vertical-gate) 起
加入**垂直门控**：本机实测高度（含下降速度前视）高于 `z_top + c_clear` 时，该障碍圆盘**不生效**；
低于顶面时圆盘**照旧生效**，故"抬高"**不能**当作通用避障手段。下面的量化说明这项改动为什么必要。

**量化**（2026-11-03，`yard` 真源逐实体实算，飞行高度按地图派生值 14 m）：

| 量 | 值 |
|---|---|
| 障碍总数 / **低于 14 m 飞行高度的** | 42 / **42（100%）** |
| 其中最高的（全图 / 包络内） | `admin_block` **10.55** / `tank_farm_e` **7.975 m** |
| 安全圆盘面积总和 | **6398 m²**（作业区 10000 m²，占 **64%**） |
| 其中"顶高 < 飞行高度、其实在脚底下"的 | **100%** |

最刺眼的单例：`wall_n` 顶高 **2.56 m**、`safety_radius` **17.0 m**
⇒ 一段 2.5 m 的矮墙在 14 m 高空挡出一个半径 17 m 的禁飞圆盘。
**⇒ 抬高度在控制层零收益**；垂直门控（ADR-0010 (j)）已消除这部分虚假圆盘。
⚠ 门控**只**解决"顶面在脚下"，**不**解决"圆形拟合差"：`wall_n` 的 17.0 m 半径主要来自
外接圆包住长薄墙，换 OBB 属另立项，且**不**降低安全层介入次数（目标间距盘不参与门控）。

因此本规范明确**分工**：

| 问题 | 靠什么解决 |
|---|---|
| 不撞障碍（水平避让） | **二维安全层 + 垂直门控**（[ADR-0010 (j)](../adr/0010-safety-thresholds-and-failsafe.md#vertical-gate)） |
| 感知能否看到目标 | **`dz`**（K1/K2，[§3.3](#perception)） |
| 视觉/几何上的"飞得比楼高"、与真实感一致 | **按地图定高**（本规范） |
| 捕获/干扰是否可达 | **K4 + 网弹道标定** |

**不得**用"提高高度"作为**通用**避障手段（门控只覆盖"顶面在脚下"这一种情形），也不得据此宣称安全层具备三维能力。

## 4. 落到配置的哪一层（避免第二份真源）

### 4.1 现状：`air.yaml` 是节点参数真源，**不是**"地图事实"的家

`air.yaml` 里的 `standoff_follower.height` / `takeoff_controller.takeoff_altitude_m` 是**节点参数**，
契约 [参数入口](../ROS2迁移交接文档.md#params) 规定由 launch **单一注入**、节点不得覆写。
但"某张地图应该飞多高"是**地图事实**，与 `world_geometry.yaml` / `maps/*.yaml` 里的
`H_max`、`work_area`、`safety_radius` 同类。把地图事实写进 `air.yaml` 会产生第二份真源
（改图忘了改高度 → 静默不一致），这正是 [ADR-0007](../adr/0007-scene-geometry-single-source-and-layout.md#top) 要消灭的病灶。

### 4.2 落地：**按地图一份**，写在同地图几何文件里，由 launch 派生注入

> ✅ **已实施**（2026-11-02，[ADR-0007](../adr/0007-scene-geometry-single-source-and-layout.md#top)）。
> 本节以下内容为设计口径原文，实现细节（含四条断言与条件派生规则）以 ADR-0007 为准。

1. **声明位置**：各地图几何文件（`src/agc_sim/config/world_geometry.yaml`（minimal）、
   `src/agc_sim/config/maps/{yard,open_field}.yaml`）顶层新增一段：

   ```yaml
   flight_altitude:            # ← 本图**固定飞行高度**的唯一真源
     own_track_m: 3.5          # 己方机跟踪高度（L2b）
     own_takeoff_m: 3.5        # 己方机起飞高度（L2c）
     target_cruise_m: 2.0      # 目标机巡航高度默认值（L2a）
     own_clearance_min_m: 0.5  # 垂直净空下限 c_clear（K3）
     derived: {h_max_env_m: 2.10, h_max_map_m: 10.55, rule_version: 1}
   ```

2. **地图 ↔ 文件的对照表不加第二份**：仍只经
   [`src/agc_sim/launch/world_map.py`](../../src/agc_sim/launch/world_map.py) 的 `MAP_GEOMETRY_FILES` 解析。
   新增地图 = 该表加一行 + 加一个 yaml + 填 `flight_altitude` 五键。

3. **谁消费**：由 `src/agc_task/launch/w6_composition.py` 新增一个 `apply_flight_altitude(air_merged, geometry)`，
   与既有的 `apply_air_geometry`（把障碍几何注入 `trajectory_tracker.safety`）**同款同位置**：
   在 `w6.launch.py` 的 air 合并之后、`assertions()` 之前调用，把
   `standoff_follower.height`、`takeoff_controller.takeoff_altitude_m` 覆盖为地图值，
   并把 `intruder_driver.cruise_alt_m` **覆盖**为地图值。
   ⚠ H0 时代"场景显式声明优先、`source=scene`"的要求**已作废**（ADR-0007 改为 `source=map`）：
   现在**地图值优先**，场景层若硬编码 `cruise_alt_m` 会被 `tests/test_scene_config_invariants.py`
   判失败。
   `air.yaml` 保留同名参数作 **standalone / 单测兜底**，并在注释里写明"运行期由几何真源派生注入"，
   与既有 `safety.obstacle_*` 的处理完全一致（那边已经这么做了，可直接照抄）。

4. **守护断言**（并入 `assertions()`，误配即**拒绝运行**）：
   `flight_altitude_derived_matches_source`（注入值 == 地图文件值）、
   `own_height_covers_h_max_env`（`own_track_m ≥ h_max_env_m + own_clearance_min_m`）、
   `target_within_capture_envelope`（触发了 capture/jam 的场景才判 K4）。
   `dz_within_perception_range` 已于 2026-11-06 删除：它读的 `sensors_file` 随 `perception`
   轴退役，且 K1 本就不在运行期生效（见 §3.2），删它不改变任何判定。

5. **为什么不是新建一个 `flight_altitudes.yaml`**：会引入"几何文件 ↔ 高度文件"两处需同步的清单，
   与"单一清单"纪律冲突；而把高度放进几何文件，改图时**同一处**就能看到高度是否还成立。

## 5. 新地图 / 新场景的复用步骤（可直接照做的清单）

1. **画图**：按 [地图设计规范](目录与命名规范.md) 与 `map-design` 技能落几何；`MAP_GEOMETRY_FILES` 加一行。
2. **算三个数**（脚本：[`height_survey.py`](../../.coordination/task/20261102-002-n1-vision-minimal-loop/round-7/evidence/height_survey.py) 的同款逻辑）：
   `H_max_map`（全图）、`H_max_env`（作业包络内）、以及**目标路径若会移动**时的 `H_max_env(moving)`。
3. **定 `h_t`**：先按场景语义定目标机高度，再**必须**验 K4（`≤ applicable_max_alt_m`）。超了就停：
   要么不抬目标机，要么先重标定网弹道。
4. **定 `h_o`**：取 `max( h_max_env + c_clear , h_t )`，再验 K1（`|h_o − h_t| ≤ 28.21 m`，R=30）与 **K2（`≤ 7.14 m`，现行先绑定者）**。
   **两者冲突时不得单方面取舍**——那是"要越障"与"要看得见"之间的目标级取舍，交用户裁定。
5. **填 `flight_altitude` 五键**，跑 `python3 tests/w6_geometry_check.py`（几何派生一致性）。
6. **断言守护**：确认 `assertions()` 的四条（[§4.2](#where) 第 4 点）在新地图上为 `true`。
6.5 **证据可比性**（**独立于高度，但同一条链上的坑**）：新地图/新场景的每次运行，探针必须**统一**采集
   `pairing_chain.track_records` + `gt_target_samples`（round-7 实测：成功 run 的旧探针缺这两项 ⇒
   **无法与失败 run 做同款对齐**，"失败 run 误差更大"只能靠间接指标支持）。
   一 run 一目录、逐份标 `run_id` + `launch_pid`（round-6 因混装两次 run 被裁定 `待返工`）。
7. **场景侧**：反无人机场景按 [§2](#no-fixed-trajectory) 设 `HoverTrajectory`。
   **高度不在场景层声明**——[ADR-0007](../adr/0007-scene-geometry-single-source-and-layout.md#top) 已把
   权威来源改为**地图**（`source=map`），H0 时代的「场景显式声明 `cruise_alt_m`、`source=scene`」
   要求**已作废**；在场景层硬编码高度会被 `tests/test_scene_config_invariants.py` 判失败。

### 6.1 `yard` 的两种形态（这是本轮唯一真正需要用户裁定的数）

- **静止目标（s04 形态）**：严格判据 `H_max_env = 2.10 m`（`pipe_rack_e` 顶，距目标 10.34 m）。
  **但紧邻环带外**还有 `hut_s`（2.56 m，距 11.31 m）、`container_yard_b`（2.59 m，距 14.78 m）——
  `hut_s` 只超出 `safe_max = 11.2` **0.11 m**，边界余量不足（视觉航迹偏 1 m 就会把它算进包络）。
  故按 `hut_s` 定：`h_o ≥ 2.56 + c_clear(0.5) = 3.06` ⇒ 取 **3.5 m**；`dz = 1.5 m`，
  水平预算 `11.91 m ≥ 10.2` ✓、俯仰角 `+8.4° ≤ 35°` ✓、`h_t = 2.0 ≤ 2.009` ✓。**全绿。**
  （这是为什么建议值不直接取 `2.10 + 0.5 = 2.60`：判据必须含**边界余量**，见 [§5](#reuse) 第 2 步。）
- **目标会平移（s02 形态，目标移到 x≈30）**：`H_max_env = 7.97 m`（`tank_farm_e`）。
  要越过它需 `h_o ≥ 7.97 + c_clear`；K1（R=30）给 `h_o ≤ h_t + 28.21`，**不绑定**；
  **K2 相机垂直视场**给 `h_o ≤ h_t + 7.14`。取 `h_t = 2.009`（K4 上限）⇒ `h_o ≤ 9.15 m`。
  ⇒ 需 `7.97 + c_clear ≤ 9.15` ⇔ **`c_clear ≤ 1.18 m`**。现行 `c_clear = 0.5` **满足**，该形态**可行**。
  （历史注记：量程为 12.0 时的旧结论是 `c_clear ≤ 0.35 m`，已随量程修正作废。）
  两个可行方向（**均需用户裁定，本轮不做**）：
  1. 把 `c_clear` 定在 ≤ 0.35 m，接受极薄净空；
  2. 不追求越障，改为**约束目标路径**不进入 `tank_farm_e` 的包络（改场景/地图，属目标级变更）；
  3. 抬目标机 —— 被 K4（2.009 m）挡住，除非先重标定网弹道。

### 6.2 关于"yard 2.5 m 飞得比 10.55 m 的楼低"

这是**真实感与视觉合理性**的硬证据，成立；但按 [§3.5](#perception) 它**不是**用高度能修的避障问题——
`s04` 的实际作业包络内最高只有 2.10 m。若用户要求"演示时明显高于建筑"，
那是**演示口径**（改 `h_o` 到 ≈11 m）而非工程约束。现行 `yard` 已取 14/12（见地图真源 `flight_altitude`），
K1（R=30）的 `dz` 上限 28.21 m **够用**；K2 的 7.14 m 也够（`dz=2.0`）。
⚠ 真正的天花板是 **K4**：目标机一旦 >2.009 m 就必须先按 [§3.4](#capture) 重标定网弹道与干扰包络。

### 3.6 「识别高度」到底有没有用（2026-11-03 口径澄清）

同一轮讨论里被问过的问题，答案**与直觉相反**，记下来避免重复投入：

| 用途 | 识别高度有没有用 | 依据 |
|---|---|---|
| **正俯视测图**（障碍 XY 进 `/agc/map`） | **没用，且不参与计算** | 铅直向下时点的画面位置只由 XY 决定（楼顶投影到楼基所在 XY）。`map_adapter::collectCells()` 只用 `sx`/`sy`，`sz` 从不参与 |
| **前视跟踪**（目标测距） | **有用，但语义是"别猜错"** | 平面假设误差按 `(h_o − z_平面)/(h_o − z_真实)` 放大：现状 2.5 m 时 0.3 m 高度误差 → **+150%**；抬到 14/12 后 → **+17.6%** |
| **无人机避障** | **有用，已用上（2026-11-04）** | 垂直门控（[§3.5](#perception)）：顶高进派生链，高于 `z_top + c_clear` 时圆盘不生效 |

**并需纠正一个常见前提**：本项目**无人机上没有激光**。全仓唯一的 `gpu_lidar` 在
[`agc_car`](../../src/agc_sim/models/agc_car/agc_car.sdf.xacro) 车顶（`car/lidar_link`，z=0.48 m）；
`x500_base` 只有 `air_pressure` / `imu` / `navsat`，可选载荷 `mono_cam` 只有 `camera`。
⇒「无人机有激光所以不必考虑避障」在本仓不成立。

> `atan(400/268.6)=56.1°`，该处径向放大 `sec²56.1°=3.22×`。二者都对，只是不是同一个量。

下面的验算回答的是「**若**将来做视觉测绘，姿态怎么选」，不代表已定方案：

**① 高度被投影成位移**。目标点投影到地面平面 `z=0` 时位移 = `高度 / tan(下视角)`：

**① 高度被投影成位移**。目标点投影到地面平面 `z=0` 时位移 = `高度 / tan(下视角)`：

| 相机下视角 | 10.55 m 的楼被"挪"多远 | 3 m 小件 |
|---|---|---|
| **90°（正俯视）** | **0** | **0** |
| 75° | 2.83 m | 0.80 m |
| 60° | 6.09 m | 1.73 m |
| **45°** | **10.55 m** | **3.00 m** |
| 30° | 18.27 m | 5.20 m |

**② 比例尺严重不均匀**（640×480，hfov 100°，H=14 m）：

| 相机 | 中心 GSD | 边缘 GSD | 不均匀度 |
|---|---|---|---|
| **正俯视** | 5.2 cm/px | 7.8 cm/px | **1.49×** |
| 斜下视 45° | 5.4 cm/px | 172.9 cm/px | **32×** |

⇒ 斜视会**破坏统一比例尺**（这是几何事实，与是否实现无关）。

**但正俯视看不见目标**：目标相对相机的仰角 `atan(dz/10.2)`，`dz=2` 时为 **11.1°**（贴地平线）；
正俯视 ±35° vfov 在 14 m 高时只能覆盖正下方 **1.4 m**（对 12 m 高空目标）——**跟踪闭环会直接断掉**。

**结论（不是方案，是约束）**：**正俯视**用于测绘最准（位移 0、GSD 均匀），但它**看不见目标**
（目标仰角只有 11.1°，14 m 高时 ±35° vfov 只覆盖正下方 1.4 m）。这两个用途**在几何上不可兼得**——
若将来真要做视觉测绘，**要么**另加一个朝下的相机，**要么**放弃用同一相机同时跟踪。
**两条都未立项**，当前一律靠真值识别。

**单目测图的固有限制（同样只是事实）**：正俯视只能拿 **XY 足迹**，**拿不到高度 Z**。
高度需**双视差**（同一点两个位置各拍一次）：基线 5 m 时，3 m 高顶面在像面移 75 px、
10.55 m 的楼移 24 px——可用但需专门设计航线。
