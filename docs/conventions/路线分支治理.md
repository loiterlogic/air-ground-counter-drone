# 路线分支治理规范

> **本文件是硬规范**：约束「同一功能出现多条可选路径」的立项、审批与退役。
> 违反本文件的分支**不得**进主链，已有分支按第 4 节清退。
>
> 约束类信息（坐标系、唯一执行口、参数入口、硬约束）**只引用**契约真源
> [ROS2迁移交接文档](../ROS2迁移交接文档.md)，本文件不复述。

<a id="why"></a>
## 1. 为什么要这条规范（问题来源）

2026-11-04 用户发现 `w6.launch.py` 有 **18 个 launch 参数**，其中 **7 个是死参数或只服务已结档研究**，
并追问"为什么会有这种多路线情况"。核查后的根因是**研究期开关未随研究结档收口**：

1. **W7-b 做 A/B 对照**（2026-11 初）需要"同场景跑不同臂"，于是加了
   `target_source` / `observe_yaw_mode` / `air_tracking_ref` / `goal_follow_target` / `shield`
   一组自变量开关；
2. **W7-b 已结档**（[ADR-0023](../adr/0023-w7b-adjudication-record-and-exit.md#top)：
   P1 `inconclusive`、P2 `falsified`），但开关**留下来了**——因为研究脚本还要能复跑；
3. **每轮新需求又叠加一层**（vision 的 `perception_path` 是第三层），**没人回头做"结档即收口"**。

后果不只是"参数多"：每个分支都是一份**独立的行为契约**，测试要覆盖两份、产物要带标识、
新读代码的人要先判断"默认走哪条"。**分支的成本随轮次复利增长，收益却随研究结档归零。**

<a id="rule"></a>
## 2. 硬规则（**没有用户明确允许，不得创造路线分支**）

### 2.1 什么叫"路线分支"

满足**任一**条件即为路线分支，受本规范约束：

- 同一**功能位置**存在 ≥2 个实现，由**参数 / 开关 / 环境变量 / 场景字段**选择；
- 新增一个 `xxx_source` / `xxx_mode` / `xxx_backend` / `xxx_path` / `xxx_type` 形式的参数；
- 用 `if 参数 == 'A'` 决定**起哪些节点**、**发哪些话题**、**写不写某个字段**；
- 同一话题出现**第二个发布者**（哪怕互斥选择）。

**不算分支**（不受约束）：

| 类别 | 例 | 理由 |
|---|---|---|
| 数值参数 | 阈值、增益、频率、`safe_max` | 不改变结构，只改变数值 |
| **场景轴** | `perception: dropout`、`obstacle: static` | 声明式测试矩阵格，进 manifest、可被不变量测试校验 |
| 地图 / 模型文件选择 | `world_map`、`px4_sim_model` | 选的是**资产**，不是**代码路径** |
| **环境适配** | `gui_render_backend`（`auto`/`d3d12`/`software`） | 按 GPU/渲染器**可用性**切换，不改变业务行为；目的是让同一份代码在不同机器跑起来 |

> **环境适配的边界**：它**不得**被用来承载业务差异（"有 GPU 时走 A 算法、无 GPU 时走 B 算法"）。
> 一旦承载业务差异，就变回路线分支，受 2.2 节约束。

### 2.2 准入条件（**四项全部满足**才算获批）

| # | 条件 | 说明 |
|---|---|---|
| ① | **用户明确允许** | 书面授权（对话 / ADR / plan 文件均可），**不得**由 Agent 自行推断"这样更灵活" |
| ② | **两条路径都有当前消费者** | "以后可能用得上"**不成立**；必须有今天就要跑的调用方 |
| ③ | **有可判定判据区分两条路径** | 产物里能证明"本 run 走了哪条"，且两条的结论不可混读 |
| ④ | **有明确的退役条件** | 写清楚"满足什么条件就删掉这条"，**不得**写"保留以备将来" |

**缺任一项 → 拒绝立项。** 特别是 ④：没有退役条件的分支**不许进主链**。

### 2.3 禁止的立项理由（已多次出现，一律驳回）

| 理由 | 为什么驳回 |
|---|---|
| "保留为可选分支，以后可能用" | 分支不会自己消失；研究结档后它变成死代码 |
| "这样更灵活 / 方便做对照" | 对照属研究期，应在**独立脚本**里做，不该进主链 launch |
| "删了研究脚本就跑不了" | 研究脚本属 `scripts/research/`（暂停未废弃），**可保留脚本、删主链开关**——脚本自己传参即可 |
| "先加上，等验证完再决定" | 验证完**必须**回头删；没删就是违约 |

<a id="retire"></a>
## 3. 分支的载体位置（越靠外越好）

同一件事有三种实现方式，**优先顺序从高到低**：

| 优先级 | 载体 | 例 |
|---|---|---|
| ① **场景轴**（最好） | `scenarios.yaml` 的 `axes` + `scenario_carriers.yaml` | `perception: dropout` → 选 `perception_sensors_dropout.yaml` |
| ② **配置文件** | 单一 yaml 的值切换，**不改节点集合** | `obstacles_source: config` |
| ③ **launch 开关**（最差，受本规范约束） | `DeclareLaunchArgument` + 节点集合变化 | `command_source` |

**为什么场景轴优于 launch 开关**：场景轴是**声明式**的、进 `scene_manifest`、能被
`test_scene_config_invariants.py` 校验；launch 开关是**命令式**的、藏在 argv 里、不进产物。

> **已观察到的反例**：`command_source` 四分支（`rl` / `baseline` / `train` / `rl_high`）
> 中，只有 `rl` 与 `baseline` 有当前消费者，另两个服务已结档的 W7。

<a id="audit"></a>
## 4. 清退规则（分支的**退役条件**）

### 4.1 强制退役触发条件（满足任一即须清退）

1. **服务的研究已结档**（ADR Status 写明"已闭合 / falsified / inconclusive"）；
2. **零调用方**——全仓无脚本 / 场景 / 文档传该参数（死参数）；
3. **两个取值的行为差异无法在产物里证明**（分不出哪条跑过，等于没有分支）；
4. **用户裁定"该能力不做"**（如 2026-11-04 视觉定位路径删除）。

### 4.2 清退动作（缺一不可）

| 步骤 | 内容 |
|---|---|
| 删代码 | launch 参数、分支体、节点、配置段 |
| 删测试 | 该分支的专项测试；**替换**为防复活闸门（见 4.3） |
| 改文档 | 契约 / ADR / README 边界 / 相关 conventions |
| 保产物 schema | 若字段已进 `summary.json` / manifest，**保留键、值固定**（见 4.4） |
| 记录 | 在 ADR 写清"删了什么、为什么、保留了什么" |

### 4.3 防复活闸门（**强制**）

每删一个分支，**必须**留一条可执行测试断言它不会被重新引入：

```python
def test_<feature>_is_retired():
    for arg in ('perception_path', 'vision_detector', 'detector_backend'):
        assert ("'%s', default_value=" % arg) not in launch_src
    assert not (ROOT / 'src' / 'agc_perception' / 'src' / 'vision_target.cpp').exists()
```

载体：`scripts/tests/test_dds_contract_guard.py`（或同目录同类文件）。
**没有闸门的删除不算完成**——下一轮会有人"顺手加回来"。

### 4.4 产物 schema 不漂移

若被删分支的标识已进对外产物（`summary.json` / `scene_manifest.json` / `report.json`），
**保留字段、值固定**：

| 情形 | 做法 | 理由 |
|---|---|---|
| 字段记录"走了哪条路径" | 保留键，值恒为唯一存活路径 | 历史 run 都带该键，删键会让新旧不可比 |
| 字段记录"用了什么模型/后端" | 保留键，值恒为 `none` / 空串 | 同上 |
| 字段是该分支专属的**结构块** | 保留块，`applied: false` | 审查仍能区分"没用"与"忘了记" |

> 实例（2026-11-04）：视觉定位路径删除后，`perception_path` / `detector_backend` /
> `vision_model` / `vision_plane` 四键**保留、值固定**，见
> [ADR-0009](../adr/0009-perception-truth-derived-and-vision-path.md#b)。

## 5. 现行分支台账（**改动此表须用户批准**）

> 本表是**唯一分支清单**。新增行 = 立项（须满足第 2.2 节四项）；删行 = 清退（须满足第 4 节）。
> 由 `scripts/tests/test_branch_ledger.py` 自动核对：**launch 里出现表外的 `xxx_source` /
> `xxx_mode` / `xxx_backend` / `xxx_path` 参数即测试失败。**

### 5.1 已批准的分支（现行，**只剩 3 个**）

| 分支参数 | 取值 | 为什么需要（消费者） | 退役条件 |
|---|---|---|---|
| `command_source` | `rl`（默认） / `baseline` | `rl` = 主控；`baseline` = Navfn+LQR 离线对照，是"路径规划"能力的唯一真实实现 | `baseline` 若被正式规划器取代 → 删 |
| `target_source` | `gt_adapter`（唯一有效值） | `gt_adapter` 用它决定自己是否发布 `/agc/targets` | 若唯一源固定，本参数可缩为常量 |
| `goal_follow_target` | 场景值（`true`/`false`） | **任务语义**：目标移动时任务目标是否跟随（ADR-0001 / ADR-0013）；s02/s03 等活跃场景依赖 | 不删——它不是实验开关 |

### 5.2 已清退（2026-11-04，全部**已删除**）

| 分支 | 处置 | 依据 |
|---|---|---|
| `perception_path`（truth / vision） | 删参数 + 删节点 `camera_tf`/`vision_target` + 删 `scripts/vision/` | 用户裁定：不做目标识别 |
| `vision_detector` / `detector_backend` / `vision_model_id` / `vision_model_name` / `vision_model_version` / `vision_model_sha256` / `target_plane_z_m` | 删 7 个参数 | 同上 |
| **`air_fusion`（整个节点）** | 删节点 + 删配置段 + `target_source` 两 backend 都改 `gt_adapter` | 用户裁定："air_fusion 也可以滚了" |
| `obstacles_source` | 删参数（恒 `config`） | `air_fusion` 退役后无第二个取值 |
| `command_source=train` | 删分支 | 服务已结档 W7（ADR-0023 P1 inconclusive） |
| `command_source=rl_high` | 删分支 | 同上；ADR-0023 记录 P2 臂 B 为负向结果 |
| `standoff_safe_max` | 删参数 | **零调用方**（死参数） |
| `spawn_randomize` | 删参数 | 仅服务 W7 训练视图 |
| `air_tracking_ref` | 删参数 | 仅服务 W7-b 对照臂 |
| `observe_yaw_mode`（**launch 参数**） | 删参数；**节点参数保留**（`velocity` / `target` / `track` 三档仍可实现） | 删的是 run 级 CLI 覆盖口。现只有「场景覆盖 > `air.yaml`」两级；`s04` 覆盖为 `track`。⚠ 此前 demo 仍传该已删参数，而 ros2 launch **静默忽略**未声明参数 ⇒ 产物声称 `target`、实际跑 `track`（2026-11-04 已修） |
| `shield` | 删参数（**安全层恒定启用**） | 无 shield 消融臂属 W7-b 研究；演示永不关安全层 |
| `px4_sim_model=gz_x500_mono_cam` | 保留参数但**已无消费者**（视觉删除后不需要相机） | 待评估是否缩为单值 |

### 5.3 已知缺陷（清退带来的，**须记住**）

| 缺陷 | 影响 | 处置 |
|---|---|---|
| **`perception` 场景轴四档失效** | `nominal`/`dropout`/`fov` 三档在 `gt_adapter` 下**行为完全相同**（`sensors_file` 只被 `air_perception` 读，而它无消费者）；`no_target` 档**无法**制造"看不见" | `scenario_carriers.yaml` 逐档标"已知缺陷"；`no_target` 标 `supported: false`；`s17` **已同步**标 `unsupported:perception`（启动期拒绝运行）并从 N3 矩阵移除（2026-11-04 对齐：此前只改承载者表，场景侧仍写 `supported`，二者矛盾）。**恢复区分力属新决策，未立项** |
| **`air_perception` 空转** | 代码保留（用户裁定"后续会有用到的地方"），但 `/agc/air/obs` 无订阅者 | 已在其 launch 文件头写明"启用时须同时补消费者" |
| **`/agc/map` 链末端无消费者** | 默认 `rl` 模式下 `map_adapter → /agc/map → costmap` 只有 `ground_baseline` 消费，而它只在 `baseline` 时启动 | 未处置——属"路径规划"主线的待建部分 |

## 6. Agent 行为约束（**本条最要紧**）

> **禁止**在实现需求时**顺手**新增路线分支。发现"这里可能需要两条路"时：

1. **停下来**，把选项与代价写进 `.coordination/CURRENT.md` 或 ADR 草案；
2. **问用户**（这是第 2.2 节条件 ① 的要求，不是建议）；
3. 得到明确允许后，**同时**在本文 5.1 表登记行，并写退役条件；
4. 未获允许就提交分支代码 = **违反本规范**，须回滚。

**特别禁止的措辞**（出现即视为未获批）：
"保留为可选分支"、"增加一个开关以便对照"、"先加上后面再决定"、
"为了兼容历史配置"、"以后可能要用"。
