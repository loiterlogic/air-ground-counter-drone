# 路线分支治理规范

> **本文件是硬规范**：约束「同一功能出现多条可选路径」的立项、审批与退役。
> 违反本文件的分支**不得**进主链，已有分支按「清退规则」节清退。
>
> 约束类信息（坐标系、唯一执行口、参数入口、硬约束）**只引用**
> [ADR-0020](../adr/0020-package-boundaries-and-runtime-topology.md)，本文件不复述。

<a id="why"></a>
## 1. 为什么要这条规范（问题来源）

2026-11-04 用户发现 `w6.launch.py` 有 **18 个 launch 参数**，其中 **7 个是死参数或只服务已结档研究**，
并追问"为什么会有这种多路线情况"。核查后的根因是**研究期开关未随研究结档收口**：

1. **研究期做 A/B 对照**（2026-11 初）需要"同场景跑不同臂"，于是加了
   `target_source` / `observe_yaw_mode` / `air_tracking_ref` / `goal_follow_target` / `shield`
   一组自变量开关；
2. **该研究已结档**（[ADR-0023](../adr/0023-adjudication-record-and-exit.md#top)：
   P1 `inconclusive`、P2 `falsified`），但开关**留下来了**——因为研究脚本还要能复跑；
3. **每轮新需求又叠加一层**（vision 的 `perception_path` 是第三层），**没人回头做"结档即收口"**。

后果不只是"参数多"：每个分支都是一份**独立的行为契约**，测试要覆盖两份、产物要带标识、
新读代码的人要先判断"默认走哪条"。**分支的成本随轮次复利增长，收益却随研究结档归零。**

<a id="rule"></a>
## 2. 硬规则（**没有用户明确允许，不得创造路线分支**）

### 2.1 什么叫"路线分支"

满足**任一**条件即为路线分支，受本规范约束：

- 同一**功能位置**存在 ≥2 个实现，由**参数 / 开关 / 环境变量 / 场景字段**选择；
- 新增一个 `xxx_source` / `xxx_mode` / `xxx_backend` / `xxx_path` / `xxx_type` 形式的参数；
- 用 `if 参数 == 'A'` 决定**起哪些节点**、**发哪些话题**、**写不写某个字段**；
- 同一话题出现**第二个发布者**（哪怕互斥选择）。

**不算分支**（不受约束）：

| 类别 | 例 | 理由 |
|---|---|---|
| 数值参数 | 阈值、增益、频率、`safe_max` | 不改变结构，只改变数值 |
| **场景轴** | `obstacle: static`、`target_motion: linear` | 声明式测试矩阵格，进 manifest、可被不变量测试校验 |
| 地图 / 模型文件选择 | `world_map`、`px4_sim_model` | 选的是**资产**，不是**代码路径** |
| **环境适配** | `gui_render_backend`（`auto`/`d3d12`/`software`） | 按 GPU/渲染器**可用性**切换，不改变业务行为；目的是让同一份代码在不同机器跑起来 |

> **环境适配的边界**：它**不得**被用来承载业务差异（"有 GPU 时走 A 算法、无 GPU 时走 B 算法"）。
> 一旦承载业务差异，就变回路线分支，受 2.2 节约束。

### 2.2 准入条件（**四项全部满足**才算获批）

| # | 条件 | 说明 |
|---|---|---|
| ① | **用户明确允许** | 书面授权（对话 / ADR / plan 文件均可），**不得**由 Agent 自行推断"这样更灵活" |
| ② | **两条路径都有当前消费者** | "以后可能用得上"**不成立**；必须有今天就要跑的调用方 |
| ③ | **有可判定判据区分两条路径** | 产物里能证明"本 run 走了哪条"，且两条的结论不可混读 |
| ④ | **有明确的退役条件** | 写清楚"满足什么条件就删掉这条"，**不得**写"保留以备将来" |

**缺任一项 → 拒绝立项。** 特别是 ④：没有退役条件的分支**不许进主链**。

### 2.3 禁止的立项理由（已多次出现，一律驳回）

| 理由 | 为什么驳回 |
|---|---|
| "保留为可选分支，以后可能用" | 分支不会自己消失；研究结档后它变成死代码 |
| "这样更灵活 / 方便做对照" | 对照属研究期，应在**独立脚本**里做，不该进主链 launch |
| "删了研究脚本就跑不了" | 研究脚本属 `scripts/research/`（暂停未废弃），**可保留脚本、删主链开关**——脚本自己传参即可 |
| "先加上，等验证完再决定" | 验证完**必须**回头删；没删就是违约 |

<a id="retire"></a>
## 3. 分支的载体位置（越靠外越好）

同一件事有三种实现方式，**优先顺序从高到低**：

| 优先级 | 载体 | 例 |
|---|---|---|
| ① **场景轴**（最好） | `scenarios.yaml` 的 `axes` + `scenario_carriers.yaml` | `obstacle: static` → 选 `obstacles.yaml` / 世界生成 |
| ② **配置文件** | 单一 yaml 的值切换，**不改节点集合** | `obstacles_source: config` |
| ③ **launch 开关**（最差，受本规范约束） | `DeclareLaunchArgument` + 节点集合变化 | `command_source` |

**为什么场景轴优于 launch 开关**：场景轴是**声明式**的、进 `scene_manifest`、能被
`test_scene_config_invariants.py` 校验；launch 开关是**命令式**的、藏在 argv 里、不进产物。

> **已观察到的反例**：`command_source` 四分支（`rl` / `baseline` / `train` / `rl_high`）
> 中，只有 `rl` 与 `baseline` 有当前消费者，另两个服务已结档的研究。

<a id="audit"></a>
## 4. 清退规则（分支的**退役条件**）

### 4.1 强制退役触发条件（满足任一即须清退）

1. **服务的研究已结档**（ADR Status 写明"已闭合 / falsified / inconclusive"）；
2. **零调用方**——全仓无脚本 / 场景 / 文档传该参数（死参数）；
3. **两个取值的行为差异无法在产物里证明**（分不出哪条跑过，等于没有分支）；
4. **用户裁定"该能力不做"**（如 2026-11-04 视觉定位路径删除）。

### 4.2 清退动作（缺一不可）

**退役对象不限于 launch 参数**：凡"功能已停用但承载物仍在活跃层"都属清退范围——
节点（可执行文件 / CMake 注册 / launch 起节点）、配置文件与变体、参数段、源码段、
场景轴与承载者、专项验收脚本、文档中的现状陈述。

| 步骤 | 内容 |
|---|---|
| 删代码 | 上述全部承载物；**解析/注入链一并删**（不能只删末端节点，留一串读不到值的透传） |
| 删测试 | 该分支的专项测试；**替换**为防复活闸门（见 4.3）。历史归档验收脚本属第 10 类产物，只读复核、**不改写**，但须在台账登记"引用已退役对象、不接活跃门槛" |
| 改文档 | 契约 / ADR / README 边界 / 相关 conventions 的**现状陈述**同步；历史评审快照与归档不重写（ADR-0002） |
| 保产物 schema | 若字段已进 `summary.json` / manifest，**保留键、值固定**（见 4.4） |
| 记录 | 在**本文件 5.2 台账**逐项登记（退役物 / 处置 / 闸门位置 / 授权与日期）；难以逆转的决策另写 ADR |

处置方式三选一，**不得含糊**：

| 方式 | 适用 | 要求 |
|---|---|---|
| **删除** | 零消费者的代码 / 配置 / 参数 | 物理移除；留防复活闸门 |
| **移归档** | 仍需复核的一次性台架 / 证据 | 进 `scripts/archive/` 或 `docs/archive/`，不留在活跃入口 |
| **保留但固定值** | 产物 schema 字段（4.4） | 键在、值恒为唯一存活路径 / `retired:<name>` / `none` |

> **授权**：「Agent 行为约束」节与「准入条件」① 要求"用户明确允许"。2026-11-06 用户在整理任务中
> 明确裁定「一并清退 / 彻底删，接受证据链变化 / 不要被限制，大胆去做」，该授权覆盖
> 5.2 表 2026-11-06 批次全部条目，并**覆盖**此前"air_perception 后续会有用到"的保留裁定。

### 4.3 防复活闸门（**强制**）

每删一个分支，**必须**留一条可执行测试断言它不会被重新引入：

```python
def test_<feature>_is_retired():
    for arg in ('perception_path', 'vision_detector', 'detector_backend'):
        assert ("'%s', default_value=" % arg) not in launch_src
    assert not (ROOT / 'src' / 'agc_perception' / 'src' / 'vision_target.cpp').exists()
```

载体：`scripts/tests/test_dds_contract_guard.py`（视觉路径）、
`scripts/tests/test_branch_ledger.py`（分支参数）、
`scripts/tests/test_retirement_ledger.py`（**退役物总台账**：节点 / 配置文件 / 场景轴 /
参数段 / 产物固定值，逐项断言"已删除者不存在、保留者带标记"）。
**没有闸门的删除不算完成**——下一轮会有人"顺手加回来"。

### 4.4 产物 schema 不漂移

若被删分支的标识已进对外产物（`summary.json` / `scene_manifest.json` / `report.json`），
**保留字段、值固定**：

| 情形 | 做法 | 理由 |
|---|---|---|
| 字段记录"走了哪条路径" | 保留键，值恒为唯一存活路径 | 历史 run 都带该键，删键会让新旧不可比 |
| 字段记录"用了什么模型/后端" | 保留键，值恒为 `none` / 空串 | 同上 |
| 字段是该分支专属的**结构块** | 保留块，`applied: false` | 审查仍能区分"没用"与"忘了记" |

> 实例（2026-11-04）：视觉定位路径删除后，`perception_path` / `detector_backend` /
> `vision_model` / `vision_plane` 四键**保留、值固定**，见
> [ADR-0009](../adr/0009-perception-truth-derived-and-vision-path.md#b)。
> 实例（2026-11-06）：`perception` 轴退役后，`manifest.effective_params.sensors_file`
> 保留键、值恒为 `retired:perception-axis`（`w6_composition.build_manifest`）。

<a id="keep"></a>
### 4.5 「保留但登记」（防止"以后会用"变成永久）

允许**保留**退役对象的情形**只有三种**，且每条必须在 5.3 台账写全四字段
（现状 / 保留理由 / 影响 / **复核触发条件**）：

| 允许保留 | 例 |
|---|---|
| 产物 schema 需兼容（4.4） | manifest / summary 的固定值键 |
| 用户**明确裁定**保留 | 待建主线的接口（见 5.3 `/agc/map`） |
| 待立项、**尚未决定** | 须写复核触发条件，不得写"保留以备将来" |

**禁止**的保留理由（2.3 节延伸）：无当前消费者、"以后可能用得上"、研究脚本还需复跑
（脚本属 `scripts/research/`，可自带参数，不该占活跃层）。

复核触发条件必须是**可判定事件**（如"全局规划主线立项时复核"），不是时间或"定期看看"。
台账条目由 `scripts/tests/test_retirement_ledger.py` 核对：登记"已删除"的路径确实不存在、
登记"保留"的文件确实带登记标记——**标记腐烂会被测试抓到**。

## 6. Agent 行为约束（**本条最要紧**）

> **禁止**在实现需求时**顺手**新增路线分支。发现"这里可能需要两条路"时：

1. **停下来**，把选项与代价写进当前交接记录或 ADR 草案；
2. **问用户**（这是「准入条件」① 的要求，不是建议）；
3. 得到明确允许后，**同时**在本文 5.1 表登记行，并写退役条件；
4. 未获允许就提交分支代码 = **违反本规范**，须回滚。

**特别禁止的措辞**（出现即视为未获批）：
"保留为可选分支"、"增加一个开关以便对照"、"先加上后面再决定"、
"为了兼容历史配置"、"以后可能要用"。
