# P0-5 · 协作成本治理（批次授权与熔断）

> 索引：[项目完成路线](README.md#plan-index)。前置：无（可与 [P0-2](p0-2-暂停迁移与基线固定.md#p0-2-goal) 并行）。
> 决策记录：[ADR-0104](../adr/0104-batch-authorization-and-stall-circuit-breaker.md)（含 [P0-5 实测后的修订](../adr/0104-batch-authorization-and-stall-circuit-breaker.md#adr-0104-amendment)）。

## 为什么做

用户 2026-10-29 反馈：**"leader 的 tokens 消耗负担不起，worker 的消耗再多我也无所谓，主要是 worker 权限和自由度太低"**。

实测证据（W8 任务 `20261027-001-w8-validation-recovery`，已归档）：

| 项 | 值 | 问题 |
|---|---|---|
| 轮次 | 24 | 每轮必唤醒 Leader |
| Leader `cacheRead` | ≈530 万 | 每次唤醒约 22 万 |
| 空转轮次 | 6（第 19–24） | 同一根因无突破 |
| 产出 | 关闭（非验收） | 25% 成本零产出 |

**结论：贵的是唤醒次数，不是审查篇幅；空转的根因是 Worker 权限太窄 + 无熔断。**

> **2026-10-29 实测修正**：上表"每次唤醒约 22 万"经实测是**单 step 上下文重读量级**；一次唤醒含 6–10 step。见下方[实测结果](#p0-5-exit)，不要把"22 万/次"继续当唤醒常数用。

## 参数

| 参数 | 值 | 含义 |
|---|---|---|
| **N** | 6 | 单次授权连续自主推进最大轮数 |
| **K** | 4 | 连续无区分性新证据触发熔断的轮数 |

## 要做什么（验证与调参）

规则改了不等于生效。需在**下一个真实任务**上验证：

1. **首次批次任务观察**：记录实际唤醒次数、批次内轮数、是否触发熔断、返工成本。
2. **对比基线**：与 W8 的 24 轮/530 万 `cacheRead` 对比，确认降幅达 75% 以上。
3. **调参判断**：
   - 若批次末常发现"方向全错、返工成本 > 省下的唤醒"，**下调 N**（如 4）或加密里程碑检查点；
   - 若熔断频繁误伤（确有进展但被判无进展），**上调 K** 或明确"区分性新证据"判据；
   - **不得**因调参取消熔断或独立验收。

| # | 判据 | 目标 | 实测 | 结果 |
|---|---|---|---|---|
| 1 | 至少 1 个真实任务按批次授权跑完，记录唤醒次数与总轮数 | 有记录 | **3 个工程轮次 / 3 次里程碑通知**（P0-3 两轮 + P0-4 一轮，均为 1:1）；另有 **2 次零执行 429 故障轮**单列，不计工程轮次 | ✅ |

**统计口径**（避免同一事件重复计数）：

| 计数项 | 值 | 说明 |
|---|---|---|
| 工程轮次 | 3 | P0-3 round-1 / round-2 / P0-4 round-1 |
| Worker→Leader 通知 | 3 | 3 轮各 1 次 `send_message`（里程碑类） |
| 运行时 settled 通知 | 7 | 与上列里程碑**同源**，不计为新事件；本批 7 次全部落在 Leader 仍在运行的 turn 内，未新增激活 |
| 返工 | 1 | P0-3 round-2（Leader 定点 6 项） |
| 零执行路由故障 | 2 | 429 配额窗口；Worker 两轮 0 step，Leader 侧同时段 2 个 error turn（其中 1 个含 4 step 诊断） |
| 越界（保留） | 3 项 | 见判据 4；按当时授权记为偏离，不追溯豁免 |
| T1 / T2 | 0 / 0 | 两个任务均未启动系统观测或真实实验 |

**实测 token 结论**：

- Leader 会话快照：11 turn / 110 step / `cacheRead` **1,886.7 万** / 未命中输入 328.3 万 / 输出 3.6 万。
- 每 step `cacheRead` 随会话上下文从约 **2.7 万** 涨到约 **36.8 万**；单次唤醒 6–10 step 故达 200–370 万。
- Worker 两任务合计 `cacheRead` **7,427.9 万**（P0-3 5,373.6 万 + P0-4 2,054.3 万），约为 Leader 同期窗口的 5 倍；与用户"Worker 消耗不是瓶颈"的裁定一致。
- 因此：**可以用 24 轮 → 3 轮描述唤醒/轮次降幅；不能据此宣称 token 降 75%**。原指标保留为未验证，**不偷改为 PASS**。

**调参结论**：

- **维持 N=6 / K=4**：本批没有"返工成本吃掉省下唤醒"的证据（1 次返工、6 项定点），也没有熔断误伤，因此缺少调整依据。
- **但也不能宣称参数已被验证**：上限未触达。下一批若仍 1–2 轮完成，应如实记录"未压测"；只有在出现 4–6 轮的批次后，N/K 才有可判的样本。
- 真正决定 token 的是**每次往返的步数与会话长度**，所以护栏重心放在"少做往返、一次审一批"（见下）。

**护栏修正（2026-10-29，来源 Leader 在已授权成本治理范围内裁定）**：

1. **离线/静态检查预算改以"总墙钟 + 单次时限 + 明确资源边界"为主**，次数只作记账观测，不作硬限、不因次数唤醒（[口径](../../.coordination/README.md#offline-budget)）。针对 P0-4"32 次 vs 18 次、而总墙钟不足 30 s"的偏离形状；**不追溯豁免 P0-4**，`T1`/`T2` 次数与闸门完全不变。
2. **提交纪律**：收尾先自查与计数核对、再一次提交回报；不为修哈希/账目自增提交；已有错误如实追加更正（P0-4 的 7 笔 vs 4 笔即此问题的实例）。
3. **重复激活按"可能重复"计**：`subagent-settled` 与 `send_message` 可能就同一里程碑各唤醒一次；本批未发生，但不作为无风险证据。
4. 规则落点：[.coordination/README.md#batch](../../.coordination/README.md#batch)、[#offline-budget](../../.coordination/README.md#offline-budget)、[leader.md#review](../../.coordination/roles/leader.md#review)、[worker.md#batch-autonomy](../../.coordination/roles/worker.md#batch-autonomy)、[ADR-0104 修订](../adr/0104-batch-authorization-and-stall-circuit-breaker.md#adr-0104-amendment)。

## 风险与注意

- **最大风险**：Worker 跑偏后一次性返工，省下的唤醒成本被返工吃掉。护栏是 K=4 熔断 + 预登记停止条件 + 证据留痕。
- **"区分性新证据"主观**：Worker 可能自我豁免。Leader 审查时须**明确裁定**，不接受"又做了一次但没结论"算新证据。
- **不要为省 token 砍验收**：独立验收是质量底线，只改频率不改标准。
- **T2 闸门不变**：全链仿真/GUI/构建仍逐轮派发，批次授权**不**放宽真实实验授权。
- **不要把"唤醒次数下降"当成"token 下降"**：本页判据 2 已实测证伪该线性关系；汇报成本须写清是轮次、唤醒次数还是 `cacheRead`。

## 非目标

- 不改 Worker 模型质量或路由（用户明确 Worker 消耗非瓶颈）。
- 不取消单任务链或一个任务一个 Worker。
- 不恢复已退役的跨进程叫醒机制。
