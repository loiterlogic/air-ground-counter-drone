# 协作机制：双模型分工与批次授权

## Status

accepted（2026-11-02 由 ADR-0102 / 0104 合并；结论未变）

## 背景

原机制是**跨工具交接**：Codex（项目主导者）与 DSH（工程执行者）分属两个进程，靠
`.coordination/scripts/coordination_wake.py` 双向叫醒，带状态守卫、固定会话绑定与 4 跳链式预算。
成本随使用暴露：要维护 `targets.json` 的会话 ID 绑定、`chain.json` 的跳数账、`wake/dsh-url` 的私有
token 交换；叫醒依赖外部 CLI 与进程判活，任一环节失效都会**静默丢消息**；用户需在两套工具间切换
上下文，DSH 侧会话必须预先绑定、不能自然延续。2026-10-28 实测确认 `51234` 服务的 token 与
`wake/dsh-url`、`~/.dsh/web.log` 记录均不匹配（均返回 401）⇒ 该链路已实际失效。

改用同进程双模型后，新的成本问题浮出：原协议「Worker 回报 → Leader 审查 → Leader 派下一轮」把
**审查单元锁成单轮**，唤醒次数与轮数 1:1。W8 验证任务 `20261027-001-w8-validation-recovery` 实测
24 轮 / 5,805 行 / 24 次唤醒，其中第 19–24 轮**连续 6 轮追同一根因无突破**、最终以「关闭（非验收）」
结档——约 25% 的轮次与成本产出为零。

## 决策

### (a) 双模型分工（同一 DSH 进程内）
| 角色 | 模型 | 职责 | 交接方式 |
|---|---|---|---|
| Leader | 不固定（会话内可切） | 讨论、诊断、裁定、派工、独立验收 | `worker` 创建，`send_message` 复用 |
| Worker | 钉死：workbuddy / `deepseek-v4.1-flash` / `max` | 实施、构建、实验、如实回报 | `send_message` 通知审查 |

核心约束：**一个任务只创建一个 Worker，后续所有轮次复用同一子会话**；子会话一轮结束只是 inactive，
冷恢复保留全部上下文。执行者路由由 Host 侧 `tool-worker` 行的 `agentOptions` 决定，与 Leader 当下
模型无关，Leader 不靠 `agent-default-model` 约束自己。

**机制事实**（均已实测）：子会话与 Leader 共享工作区、能读 `AGENTS.md`，但**看不到 Leader 的对话
历史** ⇒ 派工单必须自包含；子会话不出现在 Web 侧栏、挂在 Leader 会话头部的子会话目录下（DSH 设计，
非缺陷）；**继承不是默认**——不带 `agentOptions` 的 `subagent` 会复制 Leader 最后一次请求的
provider/model/effort，所以派工默认必须用 `worker`；白名单只约束**显式选择**，拦不住「继承 Leader 的
非白名单路由」，且**只对新会话生效**（既有会话不补采样，须新开 Leader 会话）；孙代可绕过
`tool-subagent` 检查，故另设 `worker-route-guard` 挂在 `llm/stream`、按会话 header 的
`delegationDepth` 判定，`depth >= 2` 只允许白名单路由，其余在 adapter 派发前以
`finish{kind:'error', code:'ROUTE_NOT_ALLOWED'}` 拒绝（不消耗 token）；**守卫需重启才激活**——新增的
插件行不走 HMR，改守卫代码后同样需重启。

**等待成本**：`worker` / `subagent` 工具立即返回子会话 ID、不阻塞；子会话结束时 `notifySettlement` 把
`subagent-settled` 投进 Leader 收件箱（Leader idle 走 `queue`，否则 `steer`），不需要轮询。Leader 每醒
一次都要重付整个会话上下文（idle 时零消耗，被结算通知唤醒只付 1 次短请求）⇒ **派工即结束本轮**；
需多任务时同一条消息并发派出。该规则对 Worker 派孙代同样适用。

### (b) 批次授权：成本单元从「轮次」改为「唤醒次数」
| # | 改动 | 参数 |
|---|---|---|
| 1 | **批次授权**：一次授权 Worker 连续自主推进，仅四类事件唤醒（里程碑 / 阻塞 / 预算耗尽 / 契约风险） | 记录检查点 |
| 2 | **无进展熔断**：连续无区分性新证据即停止并提交假设台账 | **K = 4** 轮 |
| 3 | **T1/T2 按批次正向授权**：一次性给批次总量（如 20 次 / 600 s），Worker 自行分配 | 批次总量 |
| 4 | **判别逻辑下放**：Leader 只给目标 / 边界 / 验收 / 预算 / 停止条件；假设排序与判别实验设计归 Worker | — |

两项强制：**预登记停止条件**——`request.md` 必须写「若 M 轮未达成 X 则判定不可测」，缺此项视为不
合规；**审查输入瘦身**——批次末 `report.md` 以 ≤30 行「审查摘要」开头，长日志只给路径。

### (c) 适用关系修订：按资源授权完成修复与验证
计数只能粗略估计排障所需工作量；把**已知根因**的修复和必要重验截在次数上限，只会增加交回与重新派工，
而不改善验收质量。因此把运行授权与规模估算分开：

- **N=6 改为记录检查点**：每六轮记录小结与资源账目，不单独触发停止或通知。
- **T1/T2 按批次正向授权**：明确允许的运行、场景 / 模式、文件与资源边界、累计及单次时间。建议次数
  仅作估算，超出须记账说明；**未授权或明确为零不得启动**。用户或派工因外部配额、费用、设备等明确
  规定的次数硬限仍须遵守并写明理由。
- **根因明确且范围、资源与时间均允许时修完验完**：有效失败用于排障，不因失败或计数单独交回。所有
  有效 / 无效 / 重试 / 重复运行均计入实际消耗，失败证据保留。
- **K=4 无进展熔断保留**：无可行判别路径时提前停，不为凑轮数重复实验；未成功不等于不可测。
- **独立任务链可按授权并行**：每链一个 Worker、返工复用；文件指定拥有者，仿真 / 构建独占，CURRENT
  由 Leader 唯一写入，逐链独立验收。总时间、资源、文件边界与契约红线随时生效。

### (d) 成本模型修正（覆盖「每次约 22 万 cacheRead」）
实测两个任务的 Leader 会话（只读 `usage` 字段）：3 次工程唤醒对应 26 step，单次唤醒 `cacheRead` 为
**202.9 万 / 357.9 万 / 368.0 万**，每 step 从约 2.7 万涨到约 36.8 万。即「22 万」实为**单 step 的
上下文重读量级**，一次唤醒含 6–10 step 且每 step 随上下文增长 ⇒ **唤醒次数是代理指标、不是成本
本身**：24 轮 → 2 轮不等于 token 按比例下降。

据此：「`cacheRead` 降幅 ≥75%」**不成立为已验证结论**（3 次工程唤醒合计 928.9 万，已高于 W8 全任务
的历史估算 530 万，而该基线本身是估算、口径不可比），保留为「未验证」，**不得**以唤醒次数比例替代
token 测量。仍成立的部分：工程轮数与通知次数可比（W8 24 轮 → 两任务合计 3 轮），路由故障 2 次单列
不计入工程轮次，返工 1 次，K=4 未触发且有「无连续无新证据轮次」的证据。**N/K 维持 6/4**——两个任务
分别用 2/6 与 1/6 轮，批次内从未出现「Worker 自定下一轮」，轮数 : 唤醒仍是 1:1，上限**从未被压测**，
既不能证明合适也不构成调参依据；调参判据改为「先看每批 step 数与上下文规模，再看轮数」。

### (e) 离线 / 静态检查预算改为资源边界为主
覆盖「次数即预算」的隐含写法：以**墙钟 + 时限 + 资源边界**为主（P0-4 按 18 次卡、实际约 32 次，而总
墙钟不足 30 s、资源边界未触碰）。次数字面越界仍记为偏离、不追溯豁免，但**新派工不再以次数为硬限或
唤醒条件**。T1/T2 的次数授权与闸门**完全不变**。

### (f) 重复激活风险
运行时 `subagent-settled` 通知与 Worker 的 `send_message` 报同一里程碑。实测本批 7 次 settled 通知
全部落在 Leader 仍在运行的 turn 内、未新增激活；但 Leader 若已 idle，同一里程碑会唤醒它两次 ⇒
**成本模型按「可能重复」计**，不以「这次没重复」作为无风险证据。

## 不做什么（边界）
- **不**保留叫醒脚本作兼容层（其投递路径依赖已失效 token 与外部 CLI，只会制造「看似可用」的假象）。
- **不**用固定会话 ID 绑定（要求用户每次手指定 Worker 会话，延续原机制的脆弱点）。
- **不**整行替换 `preset-standard`（preset 内部插件无法按嵌套 id patch，只能整行复制，升级即失效）。
- **不**取消独立验收、**不**全信 Worker 自述（任务只有经 Leader 独立审查才能验收归档，且会鼓励隐瞒）。
- **不**降低 Worker 模型质量以省钱（瓶颈在 Leader 侧唤醒次数与 Worker 自由度）。
- **不**因批次授权放宽硬约束红线、T2 真实实验闸门、单任务链。
- **不**追溯改写历史轮次的 Codex / DSH 署名。

## Considered Options
- **缩短审查篇幅** —— 被否：审查篇幅不是主要成本，**唤醒次数**才是。
- **保留固定次数硬停** —— 被否：会继续制造已知根因的往返；单纯调大次数也适配不了诊断的不确定性。
- **取消资源上限与熔断** —— 被否：会放任空转。
- **固定会话 ID 绑定 / 整行替换 preset / 保留叫醒脚本** —— 被否（见上）。
- **批次授权 + 熔断 + 下放判别 + 资源与时间硬边界 + 次数估算** —— **采纳**。

## Consequences
- **正面**：Leader 唤醒次数从 24 降到 4–6 量级；空转轮次由熔断在第 4 轮触发；Worker 自由度与权限提高，
  token 增加是**有意为之**。
- **代价 / 限制**：批次可能更长，需完整资源账目与独立审查；降低审查频率的代价是**Worker 跑偏后一次性
  返工**——三条护栏缺一不可：K=4 熔断、预登记停止条件、证据强制留痕。若实际出现「批次末发现方向全错、
  返工成本超过省下的唤醒」，应下调 N 或加密里程碑检查点，但**不得**取消熔断与独立验收。实测 token
  降幅**未证实**，不得据唤醒次数比例宣称降本。
- **删除**：`coordination_wake.py`、`start_dsh_web.py`、`dsh_workspace.py` 及其两个测试、
  `wake/targets.json`、`wake/chain.json`、`AGENTS.override.md`（Codex 专用入口）。
- **保留**：三件套（`request` / `report` / `review`）、状态机、单任务链、独立验收、T0/T1/T2 观测分级、
  Worker 自主权限边界——这些是项目资产，不随工具更换。**取消** 4 跳链式预算（原硬闸用于防跨进程无人工
  回路；现在 Leader 在每个审查点亲自裁定，防失控改由派工边界与用户授权承担，这是**放松**，需自觉维持
  单任务链纪律）。
- **风险**：Leader 与 Worker 同进程，Worker 的错误上下文不会自动进入 Leader 视野，全靠 `report.md`
  传递 ⇒ 派工单与回报的完整性要求比原机制更高。
- **未决**：① 端到端验收（新 Leader 会话 → 创建 Worker → 两轮复用 → 越权模型请求被拒）尚未执行；
  已验证「创建 + 固定路由 + 冷恢复」；② 孙代**深度**仍不受限（`workflow` 不传 `maxDepth`，只保证模型
  路由受守卫约束）；③ `worker-route-guard` 是本地 bundle（`/home/chen/.dsh-plugins-worker-route-guard/`），
  以绝对路径挂在 profile 补丁里，DSH 升级后需确认 `llm/stream` 与 `SessionHeader.delegationDepth`
  契约未变；④ N=6 / K=4 仍未被压测，首批批次任务后应记录实际唤醒次数与返工成本再定参。
