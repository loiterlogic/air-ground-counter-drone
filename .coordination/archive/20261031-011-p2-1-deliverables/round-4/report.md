<a id="p2-1-r4-defects"></a>
## 4. 本轮修的三个缺陷

### 4.1 取帧节拍被服务查询拖慢

| 项 | 事实 |
|---|---|
| 现象 | `--interval 1.0` 实际只取到 **8 帧 / 34 s**，帧间隔实测 **4.3–6.0 s** |
| 根因 | `snap()` 每次都调 `gz service -l`（全量服务查询，1–2 s）+ 文件稳定等待上限 6 s |
| 修法 | 首帧后 `check_service=False`；文件稳定步进 0.05 s / 上限 2 s；节拍按"上一次取帧起点"补足 |
| 结果 | 同样 `--interval 0.7` 取到 **23 帧**（GIF 需 ≥20） |

### 4.2 时刻基准未对齐（导致三图全选相邻帧）

| 项 | 事实 |
|---|---|
| 现象 | 三图一度全来自 `f-0003`/`f-0004`（相隔 1.7 s），不构成"三阶段" |
| 根因 | `timeline.txt` 的 `[mm:ss.d]` 是**相对运行起点**；帧时刻是 `time.monotonic()` 相对**本脚本开始轮询**——两个原点不同 |
| 修法 | 从 `result.json` 的 `started_at` 取运行起点，把帧 `mtime` 换算成同一零点 |
| 结果 | 三图落到 t≈43.8 / 45.5 / 72.6 s，**三阶段真实分开** |

### 4.3 首帧判据会把"人为拖相机"误判成"系统视角"

| 项 | 事实 |
|---|---|
| 现象 | round-4b 首帧 skyband **0.1292**（ambiguous），而 round-4 是 **0.0000** |
| 根因 | `Screenshot` 取的是 **GUI 实时视图相机**；用户拖一下画面就变。实测第 3 帧作业区 84.7%→99.9%、平均灰度差 **41.4**；第 21–22 帧窗口被放大成 1539×999 |
| 修法 | 判据改为**稳定帧 skyband 中位数**：① 只取主尺寸帧；② 与相邻帧差 >5 的跳变帧丢弃；③ 余帧取中位数（<3 帧则判不可判） |
| 结果 | 中位数 **0.0000 → top_down**，20/21 帧参与、丢弃 1 个跳变帧 |

> **这三条合起来解释了 round-2 的 0.2848 与 round-4 的 0.0000 之争**：不是"机制不同"，
> 而是"有没有人在拖相机"。round-2 那次很可能也有拖动，只是当时我没意识到这个变量。
