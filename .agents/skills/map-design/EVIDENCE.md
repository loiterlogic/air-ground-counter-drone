# 取证与失败处理（按需资源）

本文件回答："怎么证明地图真的对？出问题时按什么顺序查？"
核心纪律：**证据只取真实产物，取不到就报失败**—— 不得用旧图、示意图或"应该没问题"顶上。

## 1. 分层的证据

| 层 | 是什么 | 成本 | 什么时候要求 |
|---|---|---|---|
| **静态核查** | 解析 yaml / 比对生成世界 / 复算几何 | 秒级、纯只读 | **每次改真源都要** |
| **结构性渲染** | 真实渲染帧（GUI 视图相机，或 headless 的相机传感器），用于判"看得清、分布对" | 起 GUI 或服务端渲染 | 布局/材质定稿 |
| **运行期演示** | 全链跑通、终态符合预期 | 全链仿真 | 结构性验收 |

**越往上越贵，所以下层没过就别上上层。** 上层证据不能替代下层的断言，反之亦然。
第三层属 **T2 真实实验**：**未派发不启动**，也不得用"只是看一下"自我授权。
第二层要不要起 GUI、用哪种后端，按当次派工与[硬约束](../../../docs/ROS2迁移交接文档.md#hard-constraints)办。

### 1.1 先学后做的取证顺序

项目铁律规定的顺序，**从本机开始**：

1. **本机同版本、可运行的同类实现**（首推 Nav2 的世界，同 GZ 引擎）—— 拿"分布范式"
   （成排对齐、成列、小件成组贴功能区），**不是**拿资产；
2. **ROS 2 社区 / 官方文档**（如官方世界的 GUI 相机预设写法）；
3. **外部搜索**—— 本项目历史上用户明确裁定不作必需项（"网页看不了就不看了，学习本地能看的就行"）。

另外两个**本机就能做、成本极低**的取证：

- 引擎 schema 事实（如 PBR 字段是标量还是贴图）**读本机安装的 sdf 规格文件**，比搜教程可靠；
- 落地前先用引擎的解析器验一遍世界文件，比在 GUI 里等报错快得多。

**结论的迁移方式**：学**范式**，不抄**资产**。别人地图的尺度、分区与资产不适用于本场站。

## 2. 真实 GUI 取证

### 2.1 相机朝向必须是预设，不能靠拖

在 GUI 里累积视角操作**不可复现**，每次截图朝向都不同（用户看到"地图是斜的"就是这么来的）。
正确做法是把相机预设写进 `agc_world.sdf` 的 `<gui><plugin MinimalScene>`：

```xml
<camera_pose>0 0 &lt;h&gt; 0 1.5708 1.5708</camera_pose>
<ambient_light>...</ambient_light>
<background_color>...</background_color>
```

`pitch=+π/2` 是铅直向下；`yaw=+π/2` 使画面**北朝上、东朝右**（标准平面图）。
这个朝向不是猜的：用**同姿态相机传感器**渲染后，对几何投影做 IoU 拟合校正过
（`yaw=0` → 东朝上）。

`<h>` 只是观感取舍：太高看不清细节，太低会裁掉作业区边距。**纯视觉，不改物理与几何**。

### 2.2 截图路径：本机抓屏是堵的

本机是 **Wayland** 会话。下列手段**实测不可用**（不要再花时间试）：
`xwd` / `import` / `scrot` / `grim` / `ffmpeg` / `Xvfb` / `xdg-desktop-portal` 均未安装；
`PIL.ImageGrab` 走 X11 `XGetImage` 报 `BadMatch`；Qt/DBus 截屏拿不到窗口内容。

**可行路径**：Gazebo 自带的 `Screenshot` GUI 插件（服务 `/gui/screenshot`），
它用 ogre2 从 **3D 视图相机**取帧，不经过窗口合成器。工具：`scripts/demo/gui_capture.py`。

三个必须知道的语义（读上游源码确认过，都踩过）：

1. 服务的 `data` 是**目录**不是文件路径；传完整路径会得到"目录/时间戳.png"，永远等不到目标文件名；
2. 服务**立即**返回 `true`，但存盘在**下一个 Render 事件** → 必须轮询新文件出现，
   不能把"响应 true"当已存盘；
3. 文件刚出现时**可能还在写** → 判据是"两次采样大小相同且 > 0"再改名。

**headless 取不到 GUI 窗口截图**：`gz sim -s` 不启动 GUI 渲染客户端，`/gui/screenshot`
这类 **GUI 服务**因此不存在。但这**不等于** headless 出不了图——**相机传感器**（服务端渲染）
在 headless 下仍可渲染出帧，这是独立的一条路径，产物必须标注为传感器渲染、**不得**称作 GUI 截图。
另外：`--gui-config` 会被 `~/.gz/sim/<ver>/gui.config` 覆盖 `camera_pose`，
取到的图**不代表用户所见**，交付图不要用它。

### 2.3 证据必须标 backend

每条渲染证据都要写清它是**哪种** backend：

- `backend=gz-offscreen-camera`（或等价的相机传感器渲染）**不等于** GUI 截图，必须标注；
- 起了 GUI 就写 GUI，带了 headless 就写 headless；**headless 下用相机传感器出图是合法证据**，
  照实写 `backend` 与渲染方式即可，不是缺陷；
- 验收用哪种形态、要不要 GUI ↔ headless 等价核验，按[硬约束](../../../docs/ROS2迁移交接文档.md#hard-constraints)
  与当次派工执行（**条文不在本技能复述**）。

**不要把相机传感器渲染冒充"GUI 截图"**—— 这是伪造证据，比没有证据更糟。

## 3. 画面显示与语义层

- **GUI 保持纯场景，语义层走 RViz**：本机桥不映射 `visualization_msgs`，
  在 GUI 里叠语义层技术上走不通。`viz:=true` 会起 `viz_markers`（MarkerArray）+ `rviz2`。
- **RViz 全空且不报错** → 多半是 Fixed Frame 无效：项目话题在 `world` 系，但 TF 里没有 `world` 帧。
  解法是发一条 `map→world` 恒等静态 TF，Fixed Frame 用 `map`。
- **正俯视视图**：用 `Orbit`（`Distance` / `Pitch=1.5707` / `Yaw=0`）最不容易误设；
  `TopDownOrtho` 的 `Scale` 语义是"米/像素"，写大数会把整图压成 1 像素，看着像全空。
- **marker 必须写朝向**：复合体总朝向 = 实体 yaw + part yaw；漏掉会把长围墙画成轴对齐。
- **同一时刻只开一个 RViz / 一个 Gazebo**：关掉一个后"看起来没变化"，往往是在看另一个旧窗口。
  重启前确认进程数归零（**按 PID 杀，不要 `pkill -f`**：`-f` 会匹配到自己的命令行）。

## 4. 运行前置与常见失败

### 4.1 `GZ_SIM_SYSTEM_PLUGIN_PATH` 未定义 → launch 立刻抛异常

根因有两条，且同时存在：

1. launch 用 `EnvironmentVariable('GZ_SIM_SYSTEM_PLUGIN_PATH')` 做"追加"，该变量在
   `install/setup.bash` 里**不存在**，而 `EnvironmentVariable` 对未定义变量**抛错**；
2. 追加的 `plugin_dir` 路径算错（拼出了不存在的 `share/lib`）；真实插件在 `install/<pkg>/lib`。

短期修法：**导出正确路径**（`<ROOT>/install/agc_sim/lib`）。为什么能救：`ros_gz_sim` 的
`gz_sim.launch.py` 会把该变量与 `LD_LIBRARY_PATH` 合并后再传给 gz 进程。

**先跑 `./run_demo.sh doctor`**（只做环境预检、不起仿真）比直接 launch 快；
`run_demo.sh` / `scripts/demo/start.py` 已代为补齐该变量，正常路径不需要手动 export。

### 4.2 不要把"看起来像"当成根因

- **先复核再归因**：遇到与地图同时出现的故障，先核对**配置、进程、当前后端、内存与真实日志**，
  再判断是不是地图的问题。**不能仅凭症状**就排除地图，也不能仅凭症状直接断定是某个子系统的根因。
- 典型需要交叉核对的信号：`start rejected: air_hover_timeout`、定位发散（odom 飞掉）这类
  与飞控 / 状态估计相关的报错，**历史上**在特定后端与特定环境里出现过，被归到 PX4 / EKF 侧；
  这是**当时条件下的历史结论**，不是对所有地图、后端与未来环境的普遍因果。
  排查时按"配置 → 进程 → 后端 → 日志 → 最小复现"的顺序逐项排除，隔离状态可用独立 run 目录。
- `TypeError: takes 1 positional argument but 2 were given`（launch）→ `OpaqueFunction` 必须用
  `OpaqueFunction(function=...)`。
- 改了脚本没生效 → `install(PROGRAMS)` 是**拷贝**不是符号链接，改完要重新构建该包。

### 4.3 内存与并发（WSL 卡死时的排查顺序）

**先排除规模，但别把结论推而广之**：本项目地图的**当前规模**（几十实体 / 几百 link / 几百 KB 贴图）
对 Gazebo 属于较轻的量级；这是**量级判断**，不是"内存问题与地图永远无关"。

历史对照实验（**同一台机、当时的地图与配置**）观测到：

- 两张规模差一个量级的地图，GUI 内存都在增长且斜率接近 → 说明**在当时的条件下**，观测到的增长
  主要来自 Gazebo GUI（OGRE2 渲染）进程而非地图内容；
- 当时的放大因素包括：**同时多开 Gazebo 实例**（尤其取证渲染与演示并存）、WSL2 不主动归还
  page cache、以及高频话题 / 高频重发。

**限定**：以上只在当时的机器、后端、地图与配置下成立。换环境、换后端或加器件后要**重新测**，
不能引用这条直接判定"新地图也一定不是原因"。

纪律：

1. **取证渲染与 GUI 演示互斥**：先关演示再渲染；
2. 同一时刻只开**一个** Gazebo、**一个** RViz；
3. **演示后端按当前入口默认与当次派工执行**（当前入口默认 `full`；以入口脚本与 launch 默认值为准，
   不在技能里抄死）；`lightweight` 只在被授权时用作快速自检，**不能替代** `full` 的验收；
4. 语义层的**静态 marker 层只发一次**（TRANSIENT_LOCAL 留给后订阅者），动态层才按频率更新。

## 5. 交回口径

- 每条证据给**命令 + 退出码 + 产物路径**；长日志只给路径，不粘全文；
- **失败记录不得覆盖或删除**，包括被放弃的中间产物与"写-删"事实；
- 区分"**静态格式验证**"与"**真实加载/运行证据**"：例如"frontmatter 合法且能被发现"
  与"真的加载成功"是两件事，报告里不要混为一谈；
- 取证失败就写"未取到"，并说明缺什么授权—— 不得用别的图或旧图冒充。
