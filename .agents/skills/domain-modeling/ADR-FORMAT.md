# ADR 写法（本仓库）

ADR 放在 `docs/adr/`，编号连续：`0001-slug.md`、`0002-slug.md`…… 现状索引见 [ADR 索引](../adr/README.md#adr-index)，由 `scripts/adr_index.py` 从每篇的标题与状态生成。

## 本仓库的实际格式

```md
<a id="top"></a>          <!-- 可选；有锚点便于稳定引用 -->
# {决定的一句话标题}

## Status

accepted（{日期}，来源：用户裁定——"{原话}"）   <!-- 需要时补一句适用范围 -->

## 背景

{为什么要做这个决定：事实、实测数字、约束、评审编号}

## 决策

### (a) {子决定}
...

## Considered Options

- **{被否方案}** —— 被否：{具体理由}

## Consequences

- **正面**：...
- **代价 / 限制**：...

## 参考

- {相关 ADR 与文件，用稳定锚点}
```

**只写必要的节**：早期 ADR 有单段式的，也有一句话决策；`## Status` 是**唯一必备**节（索引要读它）。`考虑过的选项` 只在"被否方案值得记住"时写。

## Status 取值

沿用仓库既有写法，**不要发明新状态**：

| 取值 | 含义 |
|---|---|
| `accepted` | 已采纳、仍在生效 |
| `deferred` | 已裁定暂缓；后面可跟括号说明阻塞原因 |
| `superseded by ADR-NNNN` | 被新 ADR 取代（在"适用关系"节写清） |

注意：

- 状态写在 `## Status` **节里**，不是 YAML frontmatter（`--` 分隔的头部）——本仓库 105 篇 ADR 都是节形式。
- **不要替别人猜状态**：不确定就写 `deferred` 并写明未决点，不要默认写成 `accepted`。
- **暂停 ≠ 废止**：被暂停的路线其 ADR 仍是 `accepted`（决策曾经有效），暂停事实记在 plan 的开关文件里。
- 修订历史：不改旧 ADR 的结论，新增"适用关系"节或直接新开一篇并标明 `superseded by`（[ADR-0066](../adr/0066-decision-applicability-and-reference-discipline.md#decision)）。

## 编号

取 `docs/adr/` 现有最大编号 + 1，四位补零。新增后**必须**重跑：

```bash
python3 scripts/adr_index.py          # 重新生成索引
python3 scripts/adr_index.py --check  # 校验索引与 ADR 一致（非 0 = 漂移）
```

`--check` 是护城河：手改索引、忘了改索引、或改了标题都会被抓到。

## 什么时候该写 ADR

三条**同时**成立才写：

1. **难以逆转**：以后改主意的代价明显；
2. **没有上下文会奇怪**：将来的人看代码会问"当初为什么这样"；
3. **是真实取舍**：确实有别的选项，且为具体理由选了这一个。

缺一条就别写：容易逆转的以后直接改；不奇怪的没人会问；没有别的选项的没什么可记。

### 什么样的决定算

- **架构形状**：单仓、进程拓扑、消息 ABI。
- **上下文之间的集成方式**：谁通过什么接口驱动谁。
- **带锁定的技术选择**：仿真器、中间件、飞控链路——不是每个库，是"换掉要花一个季度"的那些。
- **边界与范围决定**：谁拥有哪份数据、哪些明确**不做**。
- **对显然做法的刻意偏离**：不这么做会被人当 bug"修"掉的地方。
- **代码里看不出来的约束**：外部依赖、许可、兼容性要求。
- **被否方案**：如果否掉的理由不明显，记下来，否则半年后又会被提一遍。

## 不要做

- 不要给一次性实现细节升 ADR（留在对应任务的规格/记录里）。
- 不要把 ADR 写成规格：要求、验收判据归 plan 与规格，ADR 只记"决定了什么、为什么"。
- 不要在 ADR 里复述契约约束：引用 [契约真源](../ROS2迁移交接文档.md#hard-constraints) 的稳定锚点即可。
